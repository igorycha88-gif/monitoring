# ADR-003: Коллектор Яндекс.Метрики (ЭПИК-2)

- Статус: принято
- Дата: 2026-08-14
- Связанные: ADR-001 (модель метрик), ADR-002 (паттерн коллекторов), BACKLOG.md ЭПИК-2

## Контекст

Нужен сбор трафика по сайтам из Reporting API Яндекс.Метрики (TASK-020–022):
визиты и посетители, OAuth-токен уже в `Settings.yandex_metrika_oauth_token`.
Продуктовое решение (утверждено пользователем): пишем **сегодняшний нарастающий
итог** — «живой» трафик, удобен для будущих алертов «трафик просел» (ЭПИК-7).

## Решения

### 1. Запрос к API

- `GET https://api-metrika.yandex.net/stat/v1/data` с параметрами:
  - `ids=<metrika_counter_id>`
  - `metrics=ym:s:visits,ym:s:users`
  - `date1=date2=<сегодня>` (YYYY-MM-DD, день по UTC сервера)
- Заголовок `Authorization: OAuth <token>`, timeout `metrika_timeout_seconds` (10 c).
- Без `dimensions` → одна агрегированная строка; значения берём из `totals`
  (устойчиво к пустому `data`: нет визитов → `totals == [0, 0]`).
- Пагинация не нужна (1 строка). httpx-клиент создаётся на сайт (1 запрос за цикл).

### 2. Модель метрик Prometheus

- `monitoring_site_visits_total{site, source="metrika"}` — gauge: визиты
  за текущий день (нарастающий итог с начала дня).
- `monitoring_site_visitors{site, source="metrika"}` — gauge: посетители
  за текущий день.
- Суффикс `_total` у gauge сохранён по DoD бэклога (осознанное исключение:
  имя зафиксировано в DoD). Историю по дням строит Prometheus TSDB
  (точка каждый час), лейбл с датой НЕ вводим (кардинальность).
- Точка = одна запись; один успешный сайт = 2 точки (points=2).

### 3. Rate-limit assessment (TASK-022)

> **Обновление 2026-08-14:** по запросу пользователя интервал уменьшен до
> 5 минут (`metrika_interval_seconds=300`). Пересчёт: 10 счётчиков × 12
> зап/час = ~2 880 зап/сутки — по-прежнему значительно ниже квот Reporting
> API. Механика (последовательный обход, 429/Retry-After) не меняется.

- Нагрузка: N (4–10) счётчиков × 1 запрос/час = ≤ 10–20 запросов/час
  (лимиты OAuth Reporting API Метрики — на порядки выше). Запас огромный.
- Обход сайтов последовательный (`parallel=False` — уже дефолт `BaseCollector`),
  дополнительный межсайтовый throttle не требуется.
- Интервал: `metrika_interval_seconds` = 3600 (раз в час, по DoD).

### 4. Обработка лимитов и ошибок (TASK-021)

Новый общий исключение в `collectors/base.py` (переиспользуется ЭПИК-5):

- `RateLimitError(Exception)` с полем `retry_after_seconds: float | None`.
- `BaseCollector.retry`: если поймано `RateLimitError` и `retry_after_seconds`
  задан — пауза = Retry-After (иначе обычный экспоненциальный backoff).
  Парсим только delta-seconds (HTTP-date игнорируем — Яндекс шлёт секунды).

Классы ошибок Метрики (`collectors/metrika.py`):

| HTTP | Исключение | Поведение |
|------|-----------|-----------|
| 429 | `RateLimitError(retry_after)` | ретраи (3 попытки) → ошибка коллектора |
| 401/403 | `MetrikaAuthError` | БЕЗ ретраев: токен истёк/нет прав → ошибка коллектора |
| 404 | `MetrikaNotFoundError` | счётчик не существует → без ретраев |
| 5xx/timeout/транспорт | `httpx.TransportError`/`TimeoutException` | ретраи (база) |
| кривой JSON/пустой token | `MetrikaConfigError`/`ValueError` | без ретраев |

Ошибка сайта не рвёт цикл (базовый `_collect_site_safe`):
`monitoring_collector_success=0`, `errors_total` растёт, точки не пишутся.

### 5. Сайты без счётчика и пустой токен

- Сайты без `metrika_counter_id` отфильтровываются в `__init__` коллектора
  (лог `metrika_collector_init` с `skipped_sites`); для них метрики
  `collector_*` не появляются — корректно (коллектор их не обслуживает).
- Токен пуст, но счётчики есть → коллектор регистрируется, каждый цикл
  `collect_site` бросает `MetrikaConfigError` (наблюдаемо в метриках/логах,
  а не «тихо отключён»).

### 6. Таймзона

День = UTC сервера. TZ счётчика в Метрике может отличаться (например,
Europe/Moscow) — расхождение с интерфейсом Метрики в приграничные часы
допустимо для MVP; параметр «timezone» можно добавить позже.

## Альтернативы (отклонены)

- **Вчера (закрытый день)** — отклонено пользователем: нужны живые данные.
- **Обе метрики (сегодня+вчера)** — усложнение модели, история и так в TSDB.
- **`/stat/v1/data/bytime`** — сложнее парсинг, нет выгоды для 1 дня.
- **Лейбл `date` в метриках** — рост кардинальности, история — задача TSDB.

## Риски

- Сэмплирование отчётов на больших счётчиках (для парка 4–10 сайтов маловероятно).
- Изменения API Яндекса — моки в тестах изолируют, прод-сбой виден в
  `collector_success`/`errors_total`.
- Суффикс `_total` у gauge может смутить в PromQL (`rate()` по gauge некорректен) —
  документируем в описании метрики: использовать напрямую.

## Последствия

- `collectors/base.py` расширяется (`RateLimitError`, Retry-After в `retry`) —
  с новыми unit-тестами; поведение существующих коллекторов не меняется.
- Новые файлы: `collectors/metrika.py`, `tests/test_metrika_collector.py`,
  `tests/test_base_collector.py` (дополнение).
- Затрагиваются: `app/metrics.py`, `app/config.py`, `app/main.py`, `.env.example`,
  `config/sites.yml` (комментарий-пример).
