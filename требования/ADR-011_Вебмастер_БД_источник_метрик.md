# ADR-011: Вебмастер — единый поток данных через SQLite (БД как источник метрик)

**Статус:** принято (владелец утвердил Вариант 1 + разовый promtool-импорт истории)
**Дата:** 2026-08-21
**Связанные:** ADR-004 (коллектор Вебмастера), ADR-008 (дневная динамика), ADR-009 (SQLite-хранилище)

## Контекст

Текущий поток: коллектор пишет gauge напрямую в `/metrics` (prometheus_client)
И параллельно — в SQLite (ADR-009). Проблемы:

1. **Задвоение пути записи**: значения живут в двух местах, могут разойтись.
2. **Рестарт app теряет значения** gauge до следующего прогона cron (07:00/19:00
   МСК) — панели пустуют до 12 часов.
3. **31-дневная история**, загруженная backfill'ом в SQLite (ЧТЗ_Вебмастер_Backfill_по_дням),
   не видна в Grafana: prometheus_client не умеет backfill.

Требование владельца: **одно целевое решение, старый путь убрать — без задвоений.**

## Решение

```
Яндекс.Вебмастер API → WebmasterCollector → SQLite (единый источник истины)
                                              │
                     WebmasterExporter (рендер из БД, без timestamp'ов)
                                              │
                                  /metrics ← Prometheus (scrape 15s) ← Grafana
```

### D1. БД — единственный источник; прямые записи gauge удаляются

Коллектор пишет ТОЛЬКО в SQLite (`webmaster_weekly`, `webmaster_daily`).
Записи `SEARCH_*` gauge из коллектора удаляются. Метрики
`monitoring_collector_success/duration/errors` (BaseCollector) сохраняются;
`points` = число строк, записанных в БД.

### D2. Рендер `/metrics` из БД — кастомный collector prometheus_client

`WebmasterExporter` (app/webmaster_export.py) регистрируется в REGISTRY,
отдаёт те же **имена метрик и лейблы** (дашборды/алерты не меняются):

- `monitoring_search_clicks_total / shows_total / position{site,query}` —
  последний снапшот `webmaster_weekly` (MAX(fetched_at) на site+query_id);
- `monitoring_search_daily_clicks / daily_shows{site,query}` — последняя
  дата `webmaster_daily` на site+query_id в окне `WEBMASTER_RENDER_DAYS`
  (35 дней — граница кардинальности).

None-индикатор не рендерится (не 0) — паттерн ADR-004.

### D3. Рендер без timestamp'ов + фоновое обновление кэша

Экспозиция — текущие значения БЕЗ timestamp'ов: живой Prometheus отбрасывает
семплы старше head-блока, а повторная выдача истории на каждом scrape —
шум out-of-order. Чтение SQLite — фоновым потоком
(`WEBMASTER_RENDER_REFRESH_SECONDS`, 60 с): scrape не делает I/O и не блокирует
event loop. Ошибка чтения — `STORAGE_ERRORS_TOTAL{source="webmaster-export"}` +
лог, отдаётся последний удачный кэш. Пустая/недоступная БД — метрики
отсутствуют (честное «нет данных», не нули).

### D4. История 31д — разовый импорт promtool (не рендер)

`scripts/export_webmaster_history.py`: `webmaster_daily` → OpenMetrics c
timestamp'ами (дата 00:00 UTC, дедупликация суммой по site+query+день —
разные query_id с одинаковым текстом) → `promtool tsdb create-blocks-from
openmetrics` → блоки в volume `prometheus-data` → рестарт ТОЛЬКО
monitoring-prometheus.

Границы импорта: **только daily-метрики** (weekly рендерится из БД актуальными
значениями) и **только даты строго раньше первого семпла TSDB** (стык без
дублей; первый семпл определяется по блокам TSDB/запросам). Лейблы
импортируемых серий тождественны скрейп-сериям (`job="monitoring-app"`,
`instance="app:8088"`) — блоки становятся продолжением тех же серий, `sum()`
в дашбордах не задваивается. Timestamp в OpenMetrics — **в секундах**
(промtool этого образа умножает на 1000: ms уводит блоки в 58-е тыс. лет —
фикс коммита 9ed7d15). Остатки прежнего неудачного импорта (блоки 01M0F91*,
в т.ч. `*.tmp-for-deletion`) удаляются перед новым импортом.

**Уточнение пути (инцидент 2026-08-25 «блоки молча не загружаются»):**
entrypoint НЕ передаёт `--storage.tsdb.path` → TSDB живёт в дефолтной
ПОДДИРЕКТОРИИ `data/` внутри volume (WORKDIR контейнера `/prometheus` +
дефолтный путь `data/`). Блоки класть строго в `<volume>/_data/data/`
(владелец nobody, uid 65534) — блоки в корне volume Prometheus молча
игнорирует: ни ошибок в логе, ни загрузки. При замене уже существовавших
серий порядок: `delete_series` → `clean_tombstones` → импорт блоков →
рестарт (tombstone при вертикальной компакции съедает импортированные
семплы пересекающихся серий).

### D5. Совместимость

- Имена/лейблы метрик не меняются → `grafana/dashboards/webmaster.json`,
  `prometheus/alerts.yml` (вебмастер-метрики не использует) не меняются.
- Backfill-скрипт (ЧТЗ_Вебмастер_Backfill_по_дням) остаётся валидным: он пишет
  только в БД — теперь единственный путь.
- `test_dashboards.py` (белый список метрик) расширяется именами рендера.

### D6. Dockerfile копирует scripts/

`COPY scripts ./scripts` в base-стейдж — операционные скрипты (backfill,
export истории) доступны в контейнере без `docker cp`.

## Последствия

- Рестарт app больше не теряет метрики поиска: рендер из БД оживляет панели
  сразу после старта (первый refresh — при старте).
- Удаляется класс проблем «gauge в памяти ≠ БД».
- Кардинальность рендера ограничена окном 35 дней; TSDB сохраняет историю
  дольше (retention 400d — ADR-008).

## Риски и митигация

| Риск | Митигация |
|------|-----------|
| Дубли семплов при импорте | жёсткий cutoff «до первого семпла TSDB», дедуп-сумма в экспорте |
| Блоки поверх живого TSDB | импорт в пустой каталог → mv в volume → рестарт своего контейнера |
| Out-of-order при рендере | рендер без timestamp'ов (D3) |
| БД недоступна | метрики отсутствуют + счётчик ошибок + лог; сбор в БД продолжается |

## Откат

Убрать регистрацию WebmasterExporter в main.py и вернуть прямые записи gauge
(ревизия до ADR-011). Импортированные блоки можно удалить из volume по
minTime < даты деплоя.
