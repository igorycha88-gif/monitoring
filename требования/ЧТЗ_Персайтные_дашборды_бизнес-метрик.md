# ЧТЗ (упрощённое): Персайтный дашборд бизнес-метрик — перенос user-analytics-fences (zabor-i-naves.ru)

> Версия: 1.0 · Дата: 2026-08-24
> Маршрут: Аналитик → Разработчик → Тестировщик → DevOps
> Связанные: `ЧТЗ_Подключение_zabor-i-naves.md` (мониторинг),
> `Fences of the curtain/требования/ЧТЗ_Централизованный_мониторинг.md` (сайт, дополняется v1.1)

## Задача

Перенести дашборд сайта `user-analytics-fences`
(`Fences of the curtain/grafana/provisioning/dashboards/imported/user-analytics.json`,
9 панелей) в централизованную Grafana мониторинга «в таком же виде», положив
начало механизму персональных дашбордов бизнес-метрик для каждого сайта
(метрики приложений у сайтов разные → общий шаблон невозможен, переносится
копия с фильтром по сайту).

## Исходные данные

- Дашборд: 9 панелей (5 timeseries/stat/piechart + воронка), запросы через
  `rate()/increase()` по counter-метрикам приложения:
  `analytics_events_total{event_name}`, `page_views_total`,
  `calculator_events_total`, `conversion_funnel_total{step}`.
- Метрики сайт уже отдаёт на `GET /api/metrics` (200, без ключа — закрыть по
  парному ЧТЗ §6). Все 4 метрики присутствуют (проверено 2026-08-24).
- Datasource дашборда уже `uid: prometheus` — совместим с provisioning.
- Скрейп site-content: глобальный интервал, timeout 12s — `rate[5m]` корректен.

## Решение (дизайн)

1. **Персайтные дашборды** — файлы `grafana/dashboards/site-<slug>-analytics.json`
   (для zabor: `site-zabor-analytics.json`, uid `site-zabor-analytics`,
   заголовок оригинала). В каждый запрос добавляется фильтр
   `site="<домен>"` (лейбл ставится SD/relay на серии site-* jobs) — внешний
   вид панелей не меняется; `sum by (...)` уже убирает job/instance
   (анти-задвоение, как в test_site_business_metrics_deduplicated).
2. **Данные** — через контракт ADR-007/010: kind=content. Сайту достаточно
   проксировать `location /metrics/content` → существующий `/api/metrics`
   (nginx, без изменений кода сайта) — парное ЧТЗ дополняется v1.1.
3. До реализации эндпоинта сайтом панели «No data» — ожидаемо
   (как у «Бизнес сайта» для zabor сейчас).

## Изменения (мониторинг)

1. **НОВЫЙ `grafana/dashboards/site-zabor-analytics.json`** — копия оригинала:
   - все 9 панелей, типы/тайтлы/лейауты без изменений;
   - в каждый expr добавлен `site="zabor-i-naves.ru"`;
   - refresh 30s (оригинал: нет), time now-24h как в оригинале;
   - uid/title уникальны в центральной Grafana.
2. **`tests/test_dashboards.py`** — поддержка персайтных дашбордов:
   - `PER_SITE_DASHBOARDS: dict[str, str]` (файл → домен);
   - общий тест: exprs персайтных содержат `site="<домен>"`;
   - `test_no_rate_or_increase_on_project_metrics` — без изменений
     (rate() на счётчиках приложения сайта разрешён: это не monitoring_*);
   - структурный тест: 9 панелей, метрики из известного списка сайта,
     piechart/воронка на месте.

## Изменения (сайт — парное ЧТЗ v1.1, исполняет команда сайта)

- §4.2 упрощается: `/metrics/content` = прокси существующего `/api/metrics`
  как есть (переименование в `content_*` НЕ требуется — имена метрик
  фиксированы дашбордом); `/api/metrics` закрыть ключом (§6, уже было).

## Критерии приёмки

1. `pytest && ruff check . && ruff format --check . && mypy .` — зелёные.
2. После пересборки дашборд «User Analytics - Fences» виден в Grafana
   (127.0.0.1:3300), 9 панелей, datasource prometheus.
3. Панели «No data» до готовности `/metrics/content` на сайте — норма;
   после (когда сайт включит эндпоинт) — данные появляются без правок
   мониторинга.
4. Регрессия: site-overview/all-sites/site-business/webmaster — тесты и
   панели без изменений; да-dryclean/эвакуация работают как раньше.
5. Секретов в JSON/тестах нет.

## Маршрутизация

**Архитектор:** НЕ ТРЕБУЕТСЯ (механизм скрейпа/relay ADR-007/010 не меняется;
нового источника нет — метрики уже идут через контракт site-content).
**Исполнитель:** Разработчик (JSON дашборда + тесты) → Тестировщик → DevOps
(полная пересборка). Прод-деплой — по команде владельца (PIPELINE_PROD).
