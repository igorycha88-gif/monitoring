# ADR-012: Клики по телефону — событийные метрики с точным временем из БД сайта

**Статус:** принято (владелец: источник — БД сайта, НЕ Метрика; точное время клика, обращение к сайту — раз в час допустимо)
**Дата:** 2026-08-29
**Связанные:** ADR-007 (метрики сайта за X-Monitoring-Key), ADR-010 (персайтные ключи + relay), ADR-011 (рендер из БД, запрет timestamp'ов — здесь осознанное исключение)
**Парные ЧТЗ сайтов** (индивидуально по каждому сайту, включают также
требования по недостающим метрикам из анализа полноты 2026-08-29):
ЧТЗ_Сайт_эвакуация_online_Полные_Бизнес_Метрики.md,
ЧТЗ_Сайт_zabor_i_naves_Полные_Бизнес_Метрики.md,
ЧТЗ_Сайт_da_dryclean_Полные_Бизнес_Метрики.md

## Контекст

Владельцу нужны на вкладке «Бизнес сайта»:

1. **Количество кликов по номеру телефона за 12 часов** (`tel:`-ссылки);
2. **График, показывающий ВО СКОЛЬКО был каждый клик** (точное время).

Проверка источников (2026-08-29):

- Сайты **не собирают** клики по телефону: в `business_events_24h` только
  `click_home/click_header` (эвакуация.online) и `calculator_open/contacts_view`
  (zabor-i-naves.ru); da-dryclean.ru — эндпоинт `/metrics/tracking` вообще
  не подключён (ключа нет ни локально, ни на проде).
- Метрика не подходит как источник (решение владельца): данные берём из БД сайта
  через существующий конвейер ЭПИК-9/ADR-010 (сайт → `/metrics/tracking` за
  `X-Monitoring-Key` → relay приложения → Prometheus `site-tracking`).

Требование владельца: **точное время клика**; к сайту можно обращаться
**раз в час** (кэш рендера до 60 минут допустим).

## Проблема

Существующая модель `business_*` — gauge-окна (24ч/1ч), пересчитываемые сайтом
каждые 60 с, БЕЗ timestamp'ов (философия ADR-011 D3). Такая метрика показывает
«сколько», но не «когда»: семпл получает время СКРЕЙПА, а не клика. График
«во сколько был клик» требует семплов с timestamp'ом = моменту клика.

Альтернативы отклонены:

- **Почасовые корзины в лейблах** (`{hour="13"}`) — Grafana не может отложить
  лейбл на ось времени; семпл живёт от первого скрейпа до исчезновения из окна,
  а не в момент клика.
- **Разовые уведомления/логи** — не TSDB-паттерн, нет истории для графика.

## Решение

```
Клик по tel: (JS на сайте) → events сайта (event_type="click_phone", created_at)
        │
        ▼
БД сайта ──► /metrics/tracking (кэш рендера ≤ 60 мин):
        │     ├── business_phone_clicks_12h            (gauge, окно 12ч)
        │     └── business_phone_clicks_event 1 <ts_ms> (семпл НА клик, окно 24ч)
        ▼
relay приложения (ADR-010, без изменений — тело ответа проходит насквозь)
        ▼
Prometheus site-tracking (OOO включён) ──► Grafana «Бизнес сайта»:
        │     ├── stat «Клики по телефону (12ч)»
        │     └── timeseries-бары «Клики по телефону (время клика)»
```

### D1. Регистрация события на сайте (парные ЧТЗ сайтов)

JS-делегированный обработчик клика на `a[href^="tel:"]` → существующий канал
аналитических событий сайта, `event_type="click_phone"` с точным `created_at`
в БД. Попутно клики автоматически появляются в `business_events_24h`
(существующий рендер) — панель «События по типам» их подхватит без изменений.

### D2. Две метрики экспозиции сайта

- `business_phone_clicks_12h` (gauge, без timestamp) — сумма кликов за
  последние 12 часов; пересчёт в том же 60с-цикле, что и остальные окна.
- `business_phone_clicks_event` — событийная серия: один семпл `1` с ЯВНЫМ
  timestamp'ом (мс) на каждый клик за окно рендера **24ч** (запас поверх
  12ч-панели на кэш до 60 мин и интервалы скрейпа). Семплы строго по
  возрастанию ts. Значение всегда 1 (совпадение ts+value у повторов —
  обязательное условие дедупликации, см. D3).

Рендер обеих — кэшируется тем же механизмом, что и весь `/metrics/tracking`;
сайту достаточно отдавать свежие данные раз в час (требование владельца).

### D3. Исключение из ADR-011 D3: явные timestamp'ы + out-of-order в Prometheus

Повторная выдача одного клика на каждом скрейпе (24ч подряд) — это дубликаты
(out-of-order семплы). В Prometheus 3.x в секции `storage.tsdb` задаётся
`out_of_order_time_window: 25h` (≥ окно рендера 24ч + запас):

- точные дубликаты (ts+value совпадают) молча отбрасываются — данные не
  задваиваются;
- новые клики внутри окна принимаются корректно;
- накладные расходы — 1 серия на сайт (лейбл `site` из SD), пренебрежимо.

Значение константа (1) — конфликтов «один ts, разные значения» нет by design.

### D4. Панели Grafana (+2, дашборд «Бизнес сайта» = 16 панелей)

- stat «Клики по телефону (12ч)»: `max by (site) (business_phone_clicks_12h{site="$site"})`;
- timeseries «Клики по телефону (время клика)»:
  `max by (site) (business_phone_clicks_event{site="$site"})`,
  drawStyle=bars, fillOpacity=100 — вертикальный бар в момент клика
  («во сколько кликнули» читается напрямую с оси времени).

Агрегация `max by (site)` — регрессионное требование дедупликации серий
(ЧТЗ_Фикс_Задвоение_Бизнес_Сайта).

### D5. da-dryclean.ru

`metrics_urls` уже прописаны в `config/sites.yml` — SD/relay готов. Сайту в
парном ЧТЗ: поднять `/metrics/tracking` + выдать персайтный ключ
(`SITE_METRICS_API_KEYS` в прод `.env`, ADR-010). До готовности up=0 — норма.

## Последствия

- Prometheus: `out_of_order_time_window` применяется глобально ко всем job'ам;
  остальные метрики (без явных ts) семантически не затронуты.
- Тесты: `test_dashboards.py` (16 панелей + новые метрики), `test_prometheus_config.py`
  (проверка OOO-окна ≥ 25h).
- ARCHITECTURE.md дополняется разделом о событийных метриках сайта.
- Данные появятся на панелях только после реализации сайтовой части (парные ЧТЗ);
  до этого панели «Нет данных» — честное состояние.
