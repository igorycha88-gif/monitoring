# ЧТЗ: Коллектор Яндекс.Метрики (ЭПИК-2)

- Дата: 2026-08-14
- Маршрут: Аналитик → Архитектор ✅ → Разработчик → Тестировщик → DevOps
- Основание: BACKLOG.md ЭПИК-2 (TASK-020/021/022), ADR-003
- Продуктовое решение (утверждено пользователем): метрики = **сегодня, нарастающий итог**

## 1. Цель

Сбор визитов и посетителей каждого сайта из Reporting API Яндекс.Метрики,
публикация в Prometheus для будущих дашбордов (ЭПИК-3) и алертов (ЭПИК-7).

## 2. Требования

### Функциональные

1. Каждый час (`metrika_interval_seconds=3600`) обходить все сайты из
   `config/sites.yml` с заполненным `metrika_counter_id` (последовательно).
2. Запрос: `GET https://api-metrika.yandex.net/stat/v1/data` c `ids`,
   `metrics=ym:s:visits,ym:s:users`, `date1=date2=<сегодня UTC>`,
   заголовок `Authorization: OAuth <YANDEX_METRIKA_OAUTH_TOKEN>`.
3. Значения брать из `totals` ответа; пустой ответ → нули (это данные, успех).
4. Метрики (Gauge):
   - `monitoring_site_visits_total{site, source="metrika"}` — визиты за сегодня
   - `monitoring_site_visitors{site, source="metrika"}` — посетители за сегодня
5. Сайты без `metrika_counter_id` пропускаются; `collector_*`-метрики для них
   не создаются.
6. Обработка ошибок:
   - 429 → ретраи с уважением `Retry-After` (delta-seconds), max 3 попытки,
     экспоненциальный backoff если заголовка нет; исчерпание → ошибка сайта
   - 401/403 → `MetrikaAuthError`, без ретраев
   - 404 → `MetrikaNotFoundError`, без ретраев
   - timeout/транспортные ошибки → ретраи (базовый механизм)
   - пустой токен при наличии счётчиков → `MetrikaConfigError` (коллектор
     наблюдаемо падает в метриках, а не молча отключён)
   - ошибка одного сайта не рвёт цикл
7. Базовые метрики/логи коллектора — из `BaseCollector`
   (`monitoring_collector_success/errors_total/duration_seconds`,
   `collector_cycle_start/end`, `collector_site_success/error`, `collector_retry`).

### Технические

- Новый файл `collectors/metrika.py`; класс `MetrikaCollector(BaseCollector)`,
  `source="metrika"`, `parallel=False`.
- `collectors/base.py`: добавить `RateLimitError` (поле `retry_after_seconds`);
  `retry()` при 429-исключении использует `Retry-After` вместо backoff.
- `app/metrics.py`: + `SITE_VISITS_TOTAL`, `SITE_VISITORS`.
- `app/config.py`: + `metrika_interval_seconds: int = 3600`,
  `metrika_timeout_seconds: float = 10.0`.
- `app/main.py`: регистрация `MetrikaCollector` (только если есть сайты
  со счётчиками), collectors=[...] в логе `app_started`.
- `.env.example`: + `METRIKA_INTERVAL_SECONDS`, `METRIKA_TIMEOUT_SECONDS`.
- `config/sites.yml`: комментарий-пример `metrika_counter_id`.
- Секреты только из `.env`; в коде/логах токен НЕ логировать (маскировать).

## 4. Критерии приёмки

1. `pytest && ruff check . && ruff format --check . && mypy .` — зелёные.
2. Метрики `monitoring_site_visits_total{source="metrika"}` и
   `monitoring_site_visitors{source="metrika"}` обновляются раз в час
   (проверяется тестами; в docker-деплое — presence в `/metrics`).
3. Тесты покрывают: happy path, пустой ответ (нули), 429 с Retry-After
   (пауза из заголовка, затем успех), 429 исчерпаны, 403 без ретраев, 404,
   timeout с ретраями, пустой токен, сайт без counter_id пропущен,
   логирование цикла. Покрытие новых файлов ≥ 60%.
4. Retry-After из заголовка фактически влияет на паузу (тест с замоком sleep).
5. Токен не появляется в логах/метриках/исключениях.
6. Существующие коллекторы (uptime/ssl) не меняют поведение
   (`test_base_collector.py`, `test_uptime.py`, `test_ssl_collector.py` зелёные).
7. `docker compose -p monitoring` полная пересборка — все healthy (DevOps).

## 5. Ограничения и риски

- Лимиты API: ≤10 запросов/час — запас огромный (ADR-003 §3).
- TZ: день по UTC; расхождение с TZ счётчика в приграничные часы допустимо.
- Сэмплирование отчётов Метрики на больших счётчиках — принято для MVP.
- Суффикс `_total` у gauge — осознанное следование DoD (ADR-003 §2).
