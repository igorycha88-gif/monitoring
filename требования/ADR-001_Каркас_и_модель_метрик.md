# ADR-001: Каркас приложения и модель метрик

**Дата:** 2026-08-14
**Статус:** Accepted
**Контекст:** Проект стартует с нуля. Нужен фундамент: сервис-каркас, модель метрик,
инфраструктура Docker (app + Prometheus + Grafana), на которых будут собираться
коллекторы (uptime → Метрика → Вебмастер → серверные). MVP-состав утверждён в
`требования/BACKLOG.md`.

## Решение

1. **Один сервис FastAPI** (`monitoring-app`) содержит API, `/metrics` и коллекторы,
   запускаемые in-process через APScheduler (AsyncIOScheduler).
2. **Pull-модель**: Prometheus скрейпит `app:8088/metrics` раз в 15 сек; Grafana
   читает Prometheus через provisioning (без ручной настройки UI).
3. **Единая модель метрик** с конвенцией `monitoring_<сущность>_<показатель>_<единицы>`;
   лейбл `site` обязателен для метрик сайтов; лейбл `source` (`metrika`,
   `webmaster`, `uptime`, `servers`) — для метрик здоровья коллекторов.
4. **Базовый класс коллектора** `collectors/base.py::BaseCollector`: метрики
   `monitoring_collector_*`, логи цикла, ретраи с backoff, регистрация в планировщике.
5. **Изоляция** (VPS 130.49.129.241): compose project `monitoring`, контейнеры
   `monitoring-*`, сеть `monitoring-net`, порты публикуются ТОЛЬКО на `127.0.0.1`
   (8088/9091/3300). Существующее приложение не затрагивается.

## Альтернативы

### Вариант А: Отдельный worker-процесс на коллектор
- Плюсы: изоляция сбоев, независимое масштабирование
- Минусы: N процессов/контейнеров, общий реестр метрик сложнее (нужен aggregator),
  выше эксплуатационная нагрузка. Оценка: 6/10

### Вариант Б: Prometheus скрейпит источники напрямую
- Плюсы: минимум кода
- Минусы: невозможно — Яндекс.Метрика/Вебмастер требуют OAuth, пагинацию, лимиты;
  uptime-проверки требуют исполнения кода с таймерами. Оценка: 2/10

### Вариант В (выбран): In-process коллекторы в одном FastAPI-сервисе
- Плюсы: один деплой, простота, `/metrics` из одной точки, общие ретраи/логи/метрики
- Минусы: единая точка отказа; падение коллектора не должно ронять сервис
  (митигируется try/except на уровне сайта в BaseCollector). Оценка: 9/10

## Влияние на архитектуру

### Модель метрик (ЭПИК-0 объявляет, коллекторы наполняют)
```
monitoring_collector_success{source, site}          # gauge 1/0
monitoring_collector_errors_total{source, site}     # counter
monitoring_collector_duration_seconds{source, site} # gauge
```

### Коллекторы
- Все наследуются от BaseCollector; `collect_site(site) -> int` (число точек)
- run_once: per-site try/except → метрики + логи, цикл не прерывается одним сайтом
- Ретраи: экспоненциальный backoff (3 попытки, base 1s); 429/Retry-After — в ЭПИК-2

### API (ЭПИК-0)
- `GET /health` — healthcheck
- `GET /metrics` — prometheus_client
- `GET /api/v1/sites` — список сайтов из config/sites.yml

### Инфраструктура
- Dockerfile (python:3.12-slim, uvicorn), docker-compose (app/prometheus/grafana)
- Grafana: datasource + dashboards provisioning, anonymous off

## Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Падение коллектора роняет сервис | Средняя | Высокое | try/except per-site в BaseCollector |
| Потеря in-flight сбора при рестарте | Средняя | Низкое | Идемпотентные метрики gauge/counter, повтор цикла |
| Взрыв кардинальности (query-лейблы) | Средняя | Среднее | Топ-N в ЭПИК-5, конвенция в ARCHITECTURE.md |
| Лимиты API Яндекса (429) | Высокая (позже) | Среднее | Backoff в базе, интервалы ≥ 1ч, ЭПИК-2 |
| Конфликт портов на VPS | Низкая | Высокое | Всё на 127.0.0.1, проверка ss -tlnp перед деплоем |

## Критерии успеха
- [ ] compose поднимает 3 healthy-сервиса локально
- [ ] /health, /metrics, /api/v1/sites отвечают
- [ ] pytest + ruff + mypy strict зелёные, покрытие ≥ 60%
- [ ] Метрики collector_* и логи цикла работают (подтверждено тестами)
