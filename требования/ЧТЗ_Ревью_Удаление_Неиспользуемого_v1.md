## 1. Цели и задачи

### 1.1 Бизнес-цель
Убрать мёртвый/неиспользуемый код и сервисы, выявленные при ревью проекта
«Мониторинг сайтов», чтобы снизить шум в метриках/алертах и упростить эксплуатацию.

### 1.2 Пользовательская ценность
- Метрики `monitoring_uptime_*`/`monitoring_ssl_*` и алерты `SiteDown`/`SiteSsl*`
  относятся только к реальным сайтам (da-dryclean.ru, эвакуация.online), а не к
  тестовым example.com/example.org.
- Файл `.env` не содержит мёртвых переменных.
- `docker-compose.yml` не содержит сервиса `app-dev`, который не используется
  (pytest/mypy/ruff запускаются через локальный `.venv`).
- Локальный `data/webmaster.db` (пустой файл-призрак 32 КБ) удалён — он не
  используется в Docker-режиме (контейнер пишет в volume `monitoring-db`).

### 1.3 Метрики успеха
- В `monitoring_uptime_status` и `monitoring_ssl_days_left` ровно 2 серии
  (da-dryclean.ru, эвакуация.online) вместо 4 текущих.
- `.env` не содержит `YANDEX_OAUTH_CLIENT_ID`/`YANDEX_OAUTH_CLIENT_SECRET`.
- `docker-compose.yml` не содержит сервиса `app-dev`.
- Файл `data/webmaster.db` отсутствует локально.
- `pytest && ruff check . && mypy .` проходят без регрессий.
- После пересборки: все 4 контейнера healthy, `monitoring_collector_success`
  для uptime/ssl по 2 реальным сайтам = 1.

## 2. Функциональные требования

### 2.1 User Stories с Acceptance Criteria

#### US-1: Как оператор мониторинга, я не хочу видеть метрики и алерты по тестовым сайтам example.com/example.org
**Given** в `config/sites.yml` присутствуют example.com и example.org без счётчика/вебмастера/metrics_urls
**When** разработчик убирает эти два сайта из `config/sites.yml`
**Then** `monitoring_uptime_status` содержит ровно 2 серии (da-dryclean.ru, эвакуация.online)
**And** `monitoring_ssl_days_left` содержит ровно 2 серии
**And** `monitoring_collector_success{source="uptime"}` и `{source="ssl"}` содержат ровно 2 серии
**And** алерты SiteDown/SiteSslExpiringSoon/SiteSslExpiringCritical больше не срабатывают по example.* (после устаревания метрик в TSDB)

#### US-2: Как владелец конфигурации, я хочу, чтобы `.env` не содержал мёртвых переменных
**Given** в `.env` присутствуют `YANDEX_OAUTH_CLIENT_ID` и `YANDEX_OAUTH_CLIENT_SECRET`, которые не используются в коде и не описаны в `.env.example`
**When** разработчик убирает эти две строки из `.env`
**Then** приложение запускается штатно (`monitoring-app` healthy)
**And** `pytest && ruff && mypy` проходят
**And** grep по коду не находит использований `YANDEX_OAUTH_CLIENT_ID`/`YANDEX_OAUTH_CLIENT_SECRET`

#### US-3: Как devops, я хочу, чтобы `docker-compose.yml` не содержал мёртвого сервиса app-dev
**Given** сервис `app-dev` (profile `dev`) не используется — pytest/mypy/ruff запускаются через локальный `.venv`
**When** разработчик убирает сервис `app-dev` и связанные комментарии из `docker-compose.yml`
**Then** `docker compose -p monitoring config` валиден и не содержит `app-dev`
**And** `docker compose -p monitoring up -d` поднимает ровно 4 сервиса: app, prometheus, alertmanager, grafana
**And** `docker compose -p monitoring --profile dev run --rm app-dev pytest` больше не работает (ожидаемо — удалено)

#### US-4: Как devops, я хочу убрать локальный пустой файл-призрак data/webmaster.db
**Given** локальный файл `data/webmaster.db` существует (32 КБ, 0 строк), не используется в Docker-режиме (контейнер пишет в volume `monitoring-db`), и `data/` уже в `.gitignore`
**When** разработчик удаляет локальный файл `data/webmaster.db` (и `-shm`, `-wal` при наличии)
**Then** файл отсутствует локально
**And** контейнер `monitoring-app` продолжает работать (БД в volume не затронута)
**And** `monitoring_search_*` метрики продолжают отдаваться из volume

## 3. Нефункциональные требования

### 3.1 Регрессии
- Тесты, использующие `example.com`/`example.org` во **внутренних фикстурах**
  (`tests/test_sites_config.py`, `tests/test_sites_api.py`, `tests/test_sd_api.py`),
  **НЕ затрагиваются** — они пишут свои YAML в `tmp_path` и не зависят от реального
  `config/sites.yml`. Эти тесты должны остаться зелёными.
- Дашборды Grafana, использующие переменную `site` из `label_values(monitoring_uptime_status, site)`,
  автоматически сократят список до 2 реальных сайтов — это ожидаемое и желаемое поведение.
- `ARCHITECTURE.md` и `ЧТЗ_Инфра_DevDeps_И_Хост_Тулчейн.md` (исторический документ про
  `app-dev`) **не обновляются** — ADR/ЧТЗ это проектная память, правка не требуется.
- Dockerfile stage `dev` (строки 21-35) **оставить** — это просто build-stage, не
  активный сервис. Удаление stage не даёт выгоды, а оставление сохраняет
  возможность быстрого возврата `app-dev` если понадобится.

### 3.2 Безопасность
- `.env` содержит секреты — правка только через ручное удаление двух строк,
  никаких секретов в код/коммиты не попадает.
- Существующее приложение на VPS и чужие контейнеры НЕ затрагиваются
  (см. AGENTS.md §0.1).
- Все порты остаются на `127.0.0.1`.

### 3.3 Совместимость
- `config/sites.yml` остаётся валидным по схеме `app/sites.py`.
- `docker-compose.yml` остаётся валидным по схеме Compose v3.
- Резервные пути (Prometheus, Grafana, Alertmanager) не меняются.

## 6. Риски и зависимости

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| После удаления example.* в TSDB Prometheus остаются старые серии | Высокая | Низкое | Это нормально — серии устареют после retention. Grafana-переменная `site` автоматически покажет только текущие. Можно очистить через `curl -X POST localhost:9091/api/v1/admin/tsdb/clean_tombstones` если нужно. |
| Тесты упали из-за зависимости от реального sites.yml | Низкая | Среднее | По анализу: тесты используют внутренние фикстуры. Если всё же упадут — Разработчик правит фикстуры (но не возвращаем example в sites.yml). |
| `.env` правка случайно задела другой секрет | Низкая | Высокое | Удалять строго 2 строки `YANDEX_OAUTH_CLIENT_ID` и `YANDEX_OAUTH_CLIENT_SECRET`, ничего более. |
| Контейнер monitoring-app упал после удаления локального data/webmaster.db | Очень низкая | Низкое | Контейнер использует volume `monitoring-db` (раздел 0.1 AGENTS.md), локальный файл не читается. Если упадёт — это значит контейнер использует bind-mount (что НЕ так по docker-compose.yml:16). |
| Пользователь позже захочет вернуть app-dev | Низкая | Низкое | Dockerfile stage `dev` остаётся — достаточно вернуть сервис в compose. |

### Зависимости
- Все 4 правки независимы, могут выполняться параллельно.
- TASK-TST-001 выполняется после всех правок.
- DevOps (полная пересборка) после TASK-TST-001 = GO.

## 8. Маршрутизация

**Архитектор:** НЕ ТРЕБУЕТСЯ — задача затрагивает <5 файлов (sites.yml, .env, docker-compose.yml, удаление data/webmaster.db), не вводит новых сущностей/метрик/API — только удаляет мёртвое.
**Исполнитель:** Разработчик (TASK-BCK-001, TASK-INF-001/002/003) → Тестировщик (TASK-TST-001) → DevOps (полная пересборка по Правилу 6).
**Обоснование:** Правки конфигов и compose — это уровень Разработчика + DevOps (Маршрут 1: Аналитик → Разработчик → Тестировщик → DevOps). Архитектор не нужен: модель метрик, API и источники данных не меняются.

## 9. Порядок выполнения

```
1. Разработчик:
   - TASK-BCK-001: правка config/sites.yml (убрать example.com/example.org)
   - TASK-INF-001: правка docker-compose.yml (убрать app-dev)
   - TASK-INF-002: правка .env (убрать YANDEX_OAUTH_CLIENT_ID/SECRET)
   - TASK-INF-003: удаление data/webmaster.db + shm + wal
   - TASK-TST-001: pytest && ruff check . && ruff format --check . && mypy .
   → Авто-переход к Тестировщику

2. Тестировщик:
   - Глубокая проверка: чтение каждого изменённого файла
   - Запуск pytest && ruff && mypy
   - Проверка: тесты с example.com-фикстурами не зависят от реального sites.yml
   - GO → Авто-переход к DevOps

3. DevOps:
   - Полная пересборка: docker compose -p monitoring build --no-cache
                        docker compose -p monitoring up -d --force-recreate
   - Healthcheck 4 контейнеров
   - Проверка метрик: monitoring_uptime_status = 2 серии
   - Проверка: мониторинг не затронул существующее приложение на VPS (локально — N/A)
   → Деплой завершён
```
