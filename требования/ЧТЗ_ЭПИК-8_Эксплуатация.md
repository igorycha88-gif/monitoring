# ЧТЗ: Эксплуатация — fail2ban + бэкапы (ЭПИК-8)

- Дата: 2026-08-18
- Маршрут: Аналитик → DevOps (Маршрут 3, инфраструктурная задача)
- Основание: BACKLOG.md ЭПИК-8 (TASK-080/081)
- Аудит VPS (2026-08-18): Ubuntu 22.04.2; fail2ban отсутствует; ufw inactive;
  SSH: port 22, PasswordAuthentication yes, PermitRootLogin yes;
  ~18 000 неудачных SSH-попыток за 7 дней (journalctl) — активный брутфорс;
  диск /: 13 GB свободно; порты мониторинга 8088/9091/3300 — на 127.0.0.1.

## Решения пользователя (зафиксированы)

1. `PasswordAuthentication` в SSH — **НЕ трогать** (только fail2ban).
2. Файрвол ufw — **НЕ включать** (риск для существующего приложения
   smarttraffic-*, у него открыты 80/443/8080/8388/8443; наши порты уже
   спрятаны на 127.0.0.1).
3. Состав бэкапов — **только конфиги и дашборды** (без sqlite Grafana
   и без TSDB Prometheus; код и так в git).

## 1. Цель

1. Брутфорс-атаки на SSH блокируются автоматически (fail2ban, jail sshd).
2. Конфигурация и дашборды мониторинга восстанавливаемы из резервной копии
   за минуты (ежедневный бэкап на VPS + проверенная процедура восстановления).

## 2. Требования

### TASK-080: fail2ban + аудит SSH (VPS)

1. Установить fail2ban (+ `python3-systemd` для backend=systemd) через apt
   на VPS 130.49.129.241. Системные пакеты — только эти два, согласовано
   в рамках эпика (AGENTS.md 0.1 — исключение согласовано пользователем
   решением «fail2ban на сервере» из ЧТЗ-вопросов).
2. `/etc/fail2ban/jail.local` (НЕ трогать jail.conf):
   - `[DEFAULT]`: `backend = systemd`, `banaction = iptables-multiport`;
   - `[sshd]`: `enabled = true`, `maxretry = 5`, `findtime = 10m`,
     `bantime = 1h` (повторные баны удлиняются `bantime.increment = true`,
     `bantime.factor = 2`, `bantime.maxtime = 1w`);
   - НЕТ jail'ов для чужых сервисов (nginx и т.п.).
3. `systemctl enable --now fail2ban`; статус `fail2ban-client status sshd`.
4. Записи iptables fail2ban не мешают портам 80/443/8080/8388/8443
   (правила только для заблокированных IP).
5. `ignoreip = 127.0.0.1/8` (защита от бана самого себя локально).
6. Аудит SSH оформлен отчётом в этом ЧТЗ (§5) — больше SSH не меняем.

### TASK-081: Резервные копии конфигов и дашбордов

1. `scripts/backup.sh` (в репо, rsync'ом попадает на VPS):
   - `set -euo pipefail`; лог: echo в stdout + `logger -t monitoring-backup`;
   - архивирует из `/root/monitoring/`: `config/`, `prometheus/`
     (yml + entrypoint.sh), `grafana/dashboards/`, `grafana/provisioning/`,
     `docker-compose.yml`, `Dockerfile`, `.env` (секреты!);
   - НЕТ: `app/`, `collectors/`, `tests/`, volumes (решение пользователя);
   - tar.gz → `/root/backups/monitoring/monitoring-YYYYMMDD-HHMMSS.tar.gz`,
     права `0600`, директория `0700`;
   - sha256-сумма рядом (`<архив>.sha256`);
   - ротация: хранить последние 14, старше удалять;
   - exit code != 0 при любой ошибке (для cron-почты).
2. `scripts/restore.sh <архив>`: распаковывает tar.gz в указанную
   директорию (аргумент 2, default `/root/monitoring`), проверяет sha256
   перед распаковкой, восстанавливает права `.env` → 600, печатает
   следующий шаг (`docker compose -p monitoring up -d --force-recreate`).
   ВНИМАНИЕ: restore не перезаписывает `.env` молча — только с флагом
   `--with-env`.
3. Cron на VPS (root): `0 3 * * * /root/monitoring/scripts/backup.sh >> /var/log/monitoring-backup.log 2>&1`.
4. Восстановление проверено (DoD): тестовый restore в `/tmp/restore-test`
   + `diff -r` с исходниками (кроме прав) — этап DevOps.
5. Инструкция по скачаванию бэкапа на локальную машину (scp) — в §6.

## 4. Критерии приёмки

1. `fail2ban-client status sshd` отвечает, fail2ban active+enabled,
   journal-бэкенд работает (счётчик failed растёт от брутфорса).
2. Чужое приложение (smarttraffic-*) работает как до изменений
   (сверка `docker ps` до/после).
3. `pytest && ruff check . && ruff format --check . && mypy .` — зелёные.
4. После запуска бэкапа: архив + .sha256 в `/root/backups/monitoring/`,
   права 600, внутри архива все объекты из §2-TASK-081-п.1, НЕТ volumes.
5. Ротация: при 15+ архивах остаются 14 свежих (проверено DevOps).
6. Restore-тест: sha256 сходится, `diff -r` пуст, `.env` не восстановлен
   без `--with-env`, восстановлен с ним (права 600).
7. Cron-задание установлено (`crontab -l` содержит строку 03:00).
8. Стек мониторинга работает после всех операций (healthcheck 4 сервисов).

## 6. Инструкции

Скачать свежий бэкап локально:

```bash
scp 'root@130.49.129.241:/root/backups/monitoring/monitoring-*.tar.gz' ./backups/
```

Восстановление на VPS (из архива):

```bash
/root/monitoring/scripts/restore.sh /root/backups/monitoring/monitoring-YYYYMMDD-HHMMSS.tar.gz
cd /root/monitoring && docker compose -p monitoring up -d --force-recreate
```

## 7. Риски

- fail2ban использует iptables: правилa применяются ТОЛЬКО к заблокированным
  IP (цепочка f2b-sshd), порты чужого приложения не затрагиваются.
- Бэкап содержит `.env` → права 600/700, директория недоступна другим юзерам
  (root-only).
- Потеря истории метрик при гибели VPS принята пользователем (бэкап
  только конфигов).
