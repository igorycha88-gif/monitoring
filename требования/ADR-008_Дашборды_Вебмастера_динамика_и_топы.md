# ADR-008: Дашборды Вебмастера — динамика по дням и топы запросов (срезы неделя/месяц/год)

- Статус: принято
- Дата: 2026-08-19
- Связанные: ADR-004 (коллектор Вебмастера), ADR-001 (модель метрик), ЭПИК-3 (дашборды)

## Контекст

Пользователю нужны 4 представления данных Вебмастера:

1. показы сайта в поиске **по дням**;
2. клики сайта в поиске **по дням**;
3. топ-5 запросов по **позиции** (срезы неделя/месяц/год);
4. топ-5 запросов по **кликам** (срезы неделя/месяц/год).

Ограничения API Вебмастера v4 (дополнение к ADR-004; проверено на живом
API 2026-08-19):

- `/search-queries/popular` отдаёт топ запросов **только за последнюю неделю**
  (date_from/date_to не поддерживаются) — срезов месяц/год из API нет;
- **site-level дневной истории НЕ СУЩЕСТВУЕТ** (эндпоинт
  `/search-queries/history` отвечает 404 RESOURCE_NOT_FOUND); доступна
  только **per-query** история
  `GET .../search-queries/{query_id}/history?query_indicator=&date_from=&date_to=`
  → `{indicators: {TOTAL_SHOWS: [{date: "…T00:00:00.000+03:00", value}], …}}`;
- сегодняшний день в per-query истории всегда нули (незавершён).

Решение пользователя: 2 дашборда; срезы месяц/год — приближённо из накопленной
истории Prometheus (согласовано).

## Решения

### D1. Дневная история: per-query запросы в WebmasterCollector (не новый класс)

Тот же OAuth-токен, кэш user_id, тот же daily-cron 07:00 MSK — второй
ежедневный класс-коллектор дал бы дублирование инфраструктуры без выгоды.

`collect_site` после `/popular` (у каждого запроса берётся `query_id` из
ответа) последовательно опрашивает историю каждого запроса топа:

```
GET /v4/user/{uid}/hosts/{host_id}/search-queries/{query_id}/history
    ?query_indicator=TOTAL_SHOWS&TOTAL_CLICKS
    &date_from=<сегодня - history_days + 1>&date_to=<сегодня>
```

- `webmaster_history_days: int = 7` (Settings, clamp 1..31) — окно с запасом
  на лаг обновления данных Яндекса (~1 сутки).
- **Пишутся ВСЕ завершённые дни окна** history_days каждого индикатора —
  точки с датой «сегодня» (в таймзоне Яндекса +03:00, всегда нули)
  исключаются. Изначально писалась только новейшая завершённая точка;
  изменено 2026-08-24 (инцидент «нули 21–23 августа»): агрегаты Яндекса
  финализируются с лагом более суток — день, записанный нулём, уже не
  перезаписывался никогда. Теперь каждый прогон переписывает весь window
  через upsert (site+query_id+date), ретро-корректировки подхватываются
  автоматически; доп. API-вызовов нет (ответ /history уже содержит окно).
- Сдвиг метки времени на лаг данных Яндекса одинаков для всех точек — форма
  графика корректна.
- **Лаг финализации агрегатов Яндекса** (проверено: вчера может отдаваться
  нулём при стабильных ненулевых значениях до него): коллектор запускается
  **дважды в сутки** (`webmaster_cron_hour: "7,19"`) — вечерний прогон
  перезаписывает gauge финализированным значением в том же дневном бакете
  графика; нулевой «провал» не замораживается.
- Отсутствующий индикатор в ответе — «не определён» (документировано),
  метрика не пишется (не 0). Пустой indicators — данные (успех, 0 точек).
- **404 на конкретный запрос** (QUERY_ID_NOT_FOUND — запрос выпал из выдачи
  между /popular и /history) — пропуск с warning-логом, не ошибка сайта:
  host-уровень 404 невозможен, т.к. /popular выполняется первым и уже
  отсек его. Остальные ошибки после ретраев (3) — ошибка сайта.

### D2. Метрики (gauge, лейблы `{site, query}`)

- `monitoring_search_daily_clicks{site, query}` — клики за последний
  завершённый день;
- `monitoring_search_daily_shows{site, query}` — показы за последний
  завершённый день.

Сайт-уровень = `sum()` по отслеживаемым запросам (топ-N по кликам) —
приближение к полному сайту (покрывает основную массу кликов; по показам
может занижать — запросы вне топа не учитываются), помечено в описании
дашборда. Кардинальность: 2 × top_queries (≤100) рядов на сайт — как у
 недельных метрик ADR-004.

### D3. Срезы месяц/год: avg_over_time, НЕ sum_over_time

`sum_over_time` по gauge суммирует **семплы скрейпов** (кратность интервала
15s) — значения завышены в сотни раз. Корректное приближение:

```
avg_over_time(monitoring_search_clicks_total{site=...}[$period])
```

— среднее значение недельного окна за период = «средние клики/неделю за
период». Ранжирование топов корректно, значение интерпретируемо; для
`period=7d` это точно текущее окно API. Позиция — `avg_over_time` + `bottomk`
(лучшая позиция = наименьшая). Неделя — точные данные API; месяц/год —
приближение из накопленных снапшотов, помечено в описании дашборда.

### D4. Retention TSDB: 15d → 400d

Годовой срез `[365d]` требует хранения ≥ 1 года. Флаг в docker-compose
(prometheus): `--storage.tsdb.retention.time=400d`. Оценка диска: основные
производители объёма — node_exporter/business-метрики (~2–5 тыс. активных
рядов, 15s) ≈ 5–20 МБ/день после компрессии → 400d ≈ 2–8 ГБ. DevOps при
деплое на VPS проверяет свободное место (рекомендация ≥ 5 ГБ). При нехватке —
откат retention и отказ от годового среза (дашборд работает с 30d).

### D5. Дашборды (2 файла, provisioning)

1. `webmaster-dynamics.json` (uid `webmaster-dynamics`), «Поиск: динамика
   показов и кликов»: переменная `site` =
   `label_values(monitoring_search_daily_shows, site)` (только сайты с
   Вебмастером); 2 timeseries-панели: «Показы по дням», «Клики по дням» —
   `sum(monitoring_search_daily_*{site="$site"})` (сайт = сумма по
   отслеживаемым запросам, помечено в описании дашборда).
2. `webmaster-top-queries.json` (uid `webmaster-top-queries`), «Поиск: топ
   запросов»: переменные `site` (аналогично) + `period` (custom:
   Неделя=7d, Месяц=30d, Год=365d); instant-таблицы:
   - «Топ-5 запросов по позиции (лучшие)» —
     `bottomk(5, avg_over_time(monitoring_search_position{site="$site"}[$period]))`;
   - «Топ-5 запросов по кликам» —
     `topk(5, avg_over_time(monitoring_search_clicks_total{site="$site"}[$period]))`;
   - «Топ-5 запросов по показам» —
     `topk(5, avg_over_time(monitoring_search_shows_total{site="$site"}[$period]))`
     (симметричная бонус-панель, данных уже достаточно).
   В описании дашборда — пометка о приближённости срезов месяц/год.

Все ограничения конвенций ЭПИК-3 сохраняются: datasource uid `prometheus`,
`site="$site"` в каждом expr, gauge без rate()/increase().

### D6. Rate-limit assessment

+1 запрос `/user` (кэш) → без изменений; +1 `/popular` на сайт (было);
+ top_queries (≤50) per-query history запросов на сайт в день —
≈ 52 запроса/сайт/день, ≈ 520 при 10 сайтах — значительно ниже квот API
Вебмастера. Обход запросов последовательный (parallel=False).

### D7. Retention: флаг в entrypoint-скрипте (не в compose command)

`prometheus-entrypoint.sh` задаёт `--storage.tsdb.retention.time=400d` и
пробрасывает `"$@"`. Дублирование флага в compose `command` + entrypoint
ломает запуск Prometheus («flag cannot be repeated») — флаг живёт только
в entrypoint; тест фиксирует отсутствие дубля.

## Альтернативы (отклонены)

- **4 отдельных дашборда** — дробление UX; 2 дашборда покрывают все 4 среза
  (решение пользователя).
- **Новый класс WebmasterHistoryCollector** — дублирование токена/кэша/расписания.
- **sum_over_time для срезов** — суммирует семплы скрейпов, значения
  завышены на кратность скрейпа.
- **Recording rules для топов** — топ-5 не сводится заранее (topk по
  агрегату окна ≠ агрегат по topk); вычисление в момент запроса дешевле и точнее.
- **Лейбл date в метриках дня** — взрыв кардинальности (365 × N рядов/год),
  запрещено ADR-004.
- **Отдельное хранилище (SQLite) для истории** — новый контур, TSDB уже есть.
- **Site-level history эндпоинт** — не существует в API v4 (проверено:
  404 RESOURCE_NOT_FOUND); site-уровень строится суммой per-query метрик.

## Риски

- Лаг данных Яндекса: точка «вчера» может появиться через 1–2 суток —
  график сдвигается равномерно, некритично.
- Диск VPS при 400d retention — контролируется на деплое (D4), при
  нехватке retention снижается.
- Годовой срез пуст первые месяцы накопления — ожидаемо, помечено в описании.
- Изменения формата API — изолируются моками respx в тестах.
