# ЧТЗ: Фикс задвоения данных на дашборде «Бизнес сайта»

- **Дата:** 2026-08-19
- **Тип:** баг-фикс (постдеплойный рестарт, ПРАВИЛО 7)
- **Маршрут:** Аналитик → Разработчик → Тестировщик → DevOps
- **Приоритет:** высокий

## 1. Описание проблемы

После деплоя ADR-010 (переключение скрейпа метрик сайтов с прямого
`https://<домен>:443` на relay `app:8088`) на дашборде «Бизнес сайта»
(uid `site-business`) для сайта `da-dryclean.ru` в **каждой панели задвоение**
данных.

## 2. Диагностика (корневая причина)

При смене пути скрейпа изменился лейбл `instance` серий job'ов `site-*`:

| Период | instance | источник |
|---|---|---|
| до ~17:01 19.08 | `da-dryclean.ru:443` | прямой скрейп (ADR-007) |
| после ~17:05 19.08 | `app:8088` | relay (ADR-010) |

Старые серии остаются в TSDB Prometheus (последняя точка 17:01),
новые пишутся с другим `instance`. Окно дашборда — 24ч → в каждой панели
отображаются **обе** серии (различаются только `job`/`instance`) → задвоение.

Проверено через API Prometheus: `/api/v1/series?match[]=business_sessions_active`
возвращает 3 серии, из них 2 для `da-dryclean.ru` с разным `instance`.

## 3. Решение

Дашбордные запросы не должны зависеть от лейблов идентичности таргета
(`job`, `instance`). Все селекторы `business_*` и `monitoring_site_metrics_*`
на дашборде оборачиваются в агрегацию `max by (...)` без `job`/`instance`:

- простые метрики: `max by (site) (metric{site="$site"})`
- с лейблами в легенде: `max by (site, event_type) (...)`,
  `max by (site, service) (...)`, `max by (site, source) (...)`,
  `max by (site, city) (...)`, `max by (site, kind) (...)`
- топы: `topk(10, max by (site, service|city) (...))`
- `min(monitoring_site_metrics_up{site="$site"})` — уже агрегат без by, не меняется

`max` корректен: параллельные серии (старая/новая) имеют одинаковые значения,
на стыке_TIMESTAMP серии не пересекаются по времени → склейка в одну непрерывную.
Решение также устойчиво к будущим сменам таргетов скрейпа.

## 4. Критерии приёмки

1. В `grafana/dashboards/site-business.json` все expr с `business_*` и
   `monitoring_site_metrics_*` (кроме `min(monitoring_site_metrics_up...)`)
   используют `max by (...)` без сохранения `job`/`instance`.
2. Легенды `{{event_type}}`, `{{service}}`, `{{source}}`, `{{city}}`, `{{kind}}`
   продолжают работать (соответствующие лейблы остаются в `by`).
3. Регрессионный автотест: для каждого expr дашборда site-business,
   содержащего `business_` или `monitoring_site_metrics_`, проверяется
   наличие агрегации (`max by (` / `min(`), устраняющей job/instance.
4. `pytest && ruff check . && mypy .` — зелёные.
5. После редеплоя: запрос
   `max by (site) (business_sessions_active{site="da-dryclean.ru"})`
   возвращает ровно 1 серию; на дашборде задвоение отсутствует.

- Историю TSDB не трогаем (удаление серий не требуется: старые серии
