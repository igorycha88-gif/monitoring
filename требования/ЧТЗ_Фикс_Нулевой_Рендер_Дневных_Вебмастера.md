# ЧТЗ: Фикс нулевого рендера дневных метрик Вебмастера («Показы/Клики по дням»)

**Дата:** 2026-08-25
**Статус:** к выполнению
**Маршрут:** Аналитик → Разработчик → Тестировщик → DevOps (прод, PIPELINE_PROD)
**Связанные:** ADR-011 (рендер из БД), ADR-008 (дневная динамика), инцидент 2026-08-24 «нули 21–23 авг»

## Проблема

В Grafana (дашборд «Вебмастер: поиск по сайту») панели «Показы по дням» и
«Клики по дням» отображают пустой/нулевой график.

Диагностика (прод, 2026-08-25):

- `sum(monitoring_search_daily_shows)` = 0 по всем 3 сайтам; в Prometheus
  все 160 серий = 0, `max_over_time(...[30d])` = 0 за всю историю метрики
  (с 2026-08-21, деплой ADR-011);
- в SQLite `webmaster_daily` ненулевые данные ЕСТЬ (2026-08-19 = 311,
  08-20 = 287, 08-21 = 212, 08-22 = 176, 08-23 = 260 показов);
- но `WebmasterStorage.latest_daily()` рендерит по каждому (site, query_id)
  строку с MAX(date) — а самый свежий завершённый день (08-24) записан
  нулями: агрегаты Яндекса финализируются с лагом более суток, утренний
  прогон (07:00 МСК) всегда приносит «вчерашний» день ещё нулевым.

Рендер «последнего завершённого дня» без учёта лага финализации —
метрика нулевая ВСЕГДА, график — вечный ноль.

## Решение

Горизонт готовности: день считается готовым к рендеру, когда он старше
`WEBMASTER_RENDER_LAG_DAYS` (по умолчанию 2) дней относительно «сегодня»
в таймзоне Яндекса (Europe/Moscow). Данные за этот горизонт коллектор
успевает перезаписать финализированными значениями (окно history_days=7,
прогоны 07:00 и 19:00 МСК).

### TASK-BCK-1 — storage.latest_daily: верхняя граница дат

`latest_daily(since_date, until_date)` — MAX(date) вычисляется только
среди дат `<= until_date`:

```sql
WHERE date >= ? AND date <= ?
  AND date = (SELECT MAX(w2.date) FROM webmaster_daily w2
              WHERE w2.site = w.site AND w2.query_id = w.query_id
                AND w2.date <= ?)
```

### TASK-BCK-2 — WebmasterExporter + настройка лага

- `app/config.py`: `webmaster_render_lag_days: int = 2` (валидация >= 1);
- `app/webmaster_export.py`: в `refresh()` считать
  `until = (now(Europe/Moscow) - lag_days).date().isoformat()` и передавать
  в `latest_daily`;
- логировать cutoff в refresh (debug).

### TASK-FRT-3 — текст дашборда

`grafana/dashboards/webmaster.json`: описание — «лаг ~1 день» заменить на
«лаг ~2 дня (финализация агрегатов Яндекса)».

### TASK-INF-4 — DevOps (прод)

1. Полная пересборка стека по PIPELINE_PROD (rsync → build → up).
2. Восстановление истории в TSDB (нули с 21.08 нельзя перезаписать scrape'ом):
   - `delete_series` (admin API включён) для
     `monitoring_search_daily_clicks|shows` за всё время;
   - экспорт истории из БД `scripts/export_webmaster_history.py --end <D-2>`
     → promtool-импорт блоков (ADR-011 D4, timestamp в секундах);
   - рестарт только monitoring-prometheus; живой scrape продолжит серии.
3. Verify: `/metrics` отдаёт ненулевые daily-метрики; в Prometheus
   `sum(monitoring_search_daily_shows{site=...})` > 0; график в Grafana
   отображает историю с 25.07 и «ступень» последнего готового дня.

## Критерии приёмки

1. `latest_daily` не возвращает дат новее until_date (тест с нулевым
   «завтрашним» днем и ненулевым позавчерашним — рендерится позавчерашний).
2. Экспортёр рендерит значения последнего ГОТОВОГО дня, а не MAX(date).
3. `pytest && ruff check . && mypy .` — зелёные.
4. На проде: панели «Показы по дням» / «Клики по дням» показывают
   ненулевую историю (с 25.07) и актуальную «ступень».
5. Существующее приложение на сервере не затронуто (docker ps без изменений
   чужих контейнеров).

## Риски

- Лаг отображения станет честным ~2 дня (было задумано ~1) — приемлемо:
   нули хуже лага.
- Импорт блоков в TSDB — по runbook ADR-011 D4; при ошибке откат = удаление
  импортированных блоков (minTime > деплоя) + delete_series.

## Результат деплоя (2026-08-25)

- Код задеплоен (полная пересборка, все сервисы healthy); `/metrics` отдаёт
  ненулевые дневные значения последнего готового дня (23.08).
- История восстановлена импортом блоков: 23.07–23.08 (32 дня, 160 серий);
  нулевые серии 21–25.08 удалены через delete_series + clean_tombstones.
- Найден и задокументирован подводный камень: TSDB живёт в
  `<volume>/_data/data/` (дефолт `--storage.tsdb.path=data/` от WORKDIR
  `/prometheus`); блоки в корне volume игнорируются молча — уточнение
  внесено в ADR-011 D4.
