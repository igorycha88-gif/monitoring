# ЧТЗ: Фикс отображения кликов по телефону на дашборде «Бизнес» (zabor-i-naves.ru)

- Версия: 1.0
- Дата: 2026-08-29
- Маршрут: Аналитик → Разработчик → Тестировщик → DevOps (локальная пересборка + прод-деплой)
- Источник: постдеплойный репорт пользователя (Правило 7): «клики по телефону не отображаются на дашборде на проде»

## 1. Контекст

Данные в Prometheus на проде ЕСТЬ:
- `analytics_events_total{event_name="phone_click", site="zabor-i-naves.ru"}` = 5 (счётчик, живые серии)
- `business_events_24h{event_type="phone_click", site="zabor-i-naves.ru"}` = 5 (gauge 24ч)

Дашборд «Бизнес» (`grafana/dashboards/site-business.json`, ADR-012) запрашивает ДРУГИЕ метрики:
- Панель id=15 «Клики по телефону (12ч)»: `max by (site) (business_phone_clicks_12h{site="$site"})`
  → метрика существует ТОЛЬКО для эвакуация.online (= 0); для zabor-i-naves.ru серий нет → панель пустая.
- Панель id=16 «Клики по телефону (время клика)»: `max by (site) (business_phone_clicks_event{site="$site"})`
  → активных серий НЕТ ни для одного сайта (событийная серия живёт коротко после пуша) → панель пустая.

Сайты гетерогенны: каждый отдаёт бизнес-метрики в своём соглашении имён.
Дашборд должен показывать клики по телефону для ЛЮБОГО подключённого сайта.

## 2. Задача

Добавить в обе панели телефона fallback-ветки через `or` (левая ветка приоритетна —
регрессия для эвакуация.online исключена: если её метрика жива, победает она).

### Панель id=15 «Клики по телефону (12ч)» (stat, instant):

```
max by (site) (business_phone_clicks_12h{site="$site"})
or
sum by (site) (increase(analytics_events_total{event_name="phone_click", site="$site"}[12h]))
```

### Панель id=16 «Клики по телефону (время клика)» (timeseries, range, bars):

```
max by (site) (business_phone_clicks_event{site="$site"})
or
sum by (site) (increase(analytics_events_total{event_name="phone_click", site="$site"}[$__rate_interval]))
```

Замечания:
- `increase()` на счётчиках приложения сайта (business_/analytics_*) разрешён
  (`test_no_rate_or_increase_on_project_metrics` запрещает только на monitoring_*).
- Окно [12h] в stat-панели соответствует заголовку «12ч».
- Семантика `or` проверена на проде (read-only запросы):
  - zabor: `sum by (site) (increase(...[12h]))` = 1.0 (честное 12ч окно);
  - эвакуация: левая ветка возвращает серию (=0), fallback не активируется.

## 3. Файлы для изменения

1. `grafana/dashboards/site-business.json` — expr панелей id=15, id=16 (по 2 строки `or`).
2. `tests/test_dashboards.py` — `test_site_business_phone_click_panels`: новые ожидаемые expr
   (точное сравнение), плюс проверка наличия fallback-ветки `analytics_events_total`.

Код приложения не меняется: метрики уже собираются, проблема только в запросах дашборда.

## 4. Критерии приёмки

1. JSON дашборда валиден; панелей по-прежнему 16; названия панелей не изменились.
2. При `$site="zabor-i-naves.ru"`:
   - панель «Клики по телефону (12ч)» показывает значение (increase за 12ч ≈ 1);
   - панель «Клики по телефону (время клика)» строит бары по increase за range.
3. При `$site="эвакуация.online"` поведение не изменилось (левая ветка `or`).
4. `pytest && ruff check . && mypy .` — зелёные.
5. Прод: дашборд обновлён (provisioning Grafana), панели показывают клики zabor.

## 6. Риски

- `increase()` обнуляется при первом подключении скрейпа (история счётчика до старта
  скрейпа невидима) — для zabor скрейп уже идёт, TSDB прод сохраняет историю; риск принят.
- Если сайт zabor сменит формат метрик на `business_phone_clicks_*` — левая ветка
  автоматически станет приоритетной, дашборд не потребует правок.
