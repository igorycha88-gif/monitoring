# ЧТЗ (упрощённое): Подключение zabor-i-naves.ru к централизованному мониторингу

> Версия: 1.0 · Дата: 2026-08-24 · Маршрут: Аналитик → DevOps (конфигурация + пересборка; изменений кода нет)
> Парное ЧТЗ для владельца/команды сайта:
> `Fences of the curtain/требования/ЧТЗ_Централизованный_мониторинг.md`
> Решение владельца: **полный пакет сразу** (метрики site-metrics включаются до готовности сайта).

## Задача

Подключить сайт zabor-i-naves.ru (Next.js 14 + Prisma + PostgreSQL + Redis, nginx,
сервер сайта поддерживается командой сайта) полным пакетом, как da-dryclean.ru:
- uptime + SSL — автоматически после добавления домена;
- Яндекс.Метрика — счётчик **108488683** (из `.env` сайта: `NEXT_PUBLIC_YANDEX_METRIKA_ID`);
- Яндекс.Вебмастер — топ поисковых запросов;
- site-metrics — 4 kind (`tracking/content/node/postgres`) за персайтным `X-Monitoring-Key` (ADR-010).

## Исходные данные (автопроверка 2026-08-24)

| Параметр | Значение |
|---|---|
| Домен | `zabor-i-naves.ru` (ASCII, не IDN) |
| Доступность | 200 OK (nginx/1.18.0 Ubuntu, Next.js), `/api/health` → ok (database, redis) |
| TLS | Let's Encrypt, действует до 2026-11-19 (~87 дней) |
| Счётчик Метрики | `108488683` есть в `.env` сайта, **но тег на живом сайте НЕ установлен** (не найден в HTML и всех JS-чанках) → до установки тега Метрика будет отдавать 0 визитов при валидном токене (диагностика ARCHITECTURE.md §«нет данных» п.1) |
| Вебмастер | метатег верификации `b82b0cfe086d3936` присутствует в HTML сайта; хост НЕ найден в аккаунтах текущих токенов мониторинга (uid 2298186322 — только da-dryclean; uid 1145135652 — пусто) → нужен персайтный токен владельца |
| Доступ токена Метрики мониторинга к счётчику 108488683 | **403** (счётчик в другом аккаунте Яндекса) → нужен доступ/токен от владельца |
| `/metrics/{tracking,content,node,postgres}` | 404 — эндпоинтов нет, доработка командой сайта (парное ЧТЗ) |
| `/api/metrics` сайта | 200 **без ключа** — приложение уже считает prom-метрики; в парном ЧТЗ: закрыть ключом и переиспользовать для kind=content |
| Ключ site-metrics | сгенерировать персайтный (64 hex) → `.env` `SITE_METRICS_API_KEYS` (ADR-010) |

## Изменения

1. **`config/sites.yml`** — добавить сайт:
   ```yaml
   - domain: zabor-i-naves.ru
     metrika_counter_id: 108488683
     webmaster_host_id: "https:zabor-i-naves.ru:443"
     metrics_urls:
       tracking: https://zabor-i-naves.ru/metrics/tracking
       content: https://zabor-i-naves.ru/metrics/content
       node: https://zabor-i-naves.ru/metrics/node
       postgres: https://zabor-i-naves.ru/metrics/postgres
   ```
   Код не меняется (ADR-007/ADR-010: сайт подключается одной записью, SD подхватит за 60 с).
   `webmaster_host_id` — стандартная форма для ASCII-домена; уточнить по API после
   выдачи токена владельцем (GET `/v4/user/{uid}/hosts`, `verified=true`).

2. **`.env`** (не коммитить) — добавить персайтный ключ:
   `SITE_METRICS_API_KEYS` → JSON `{"эвакуация.online": "<существует>", "zabor-i-naves.ru": "<новый 64 hex>"}`.
   Ключ передаётся владельцу через защищённый канал для конфигурации nginx сайта.
   `SITE_METRICS_API_KEY` (fallback da-dryclean) не трогать.

3. **После выдачи владельцем** (отдельные правки `.env`, без изменений кода):
   - `YANDEX_WEBMASTER_OAUTH_TOKENS` += `"zabor-i-naves.ru": "<токен>"`;
   - доступ к счётчику Метрики 108488683: владелец выдаёт доступ аккаунту
     мониторинга (представитель в Метрике) ИЛИ выпускает OAuth-токен с `metrika:read`
     (у Метрики НЕТ персайтных токенов — механизм один общий
     `YANDEX_METRIKA_OAUTH_TOKEN`; если счётчик останется в другом аккаунте и
     доступ не выдан — по аналогии с эвакуация v1.1 п.3 потребуется отдельное
     решение о персайтных токенах Метрики).

## Порядок и зависимости

- uptime/SSL работают сразу после пересборки.
- Метрика: запись включена, но до выдачи доступа коллектор получает 403 для этого
  сайта → `CollectorFailing` firing (осознанное решение владельца, прецедент
  эвакуация v1.1 п.3).
- Вебмастер: токен ещё не выдан → коллектор 401 → тот же эффект.
- site-* jobs: до выполнения парного ЧТЗ командой сайта — `up=0` (404),
  `SiteMetricsEndpointDown` (warning) firing через 5 мин — ожидаемо (выбор
  «полный пакет сразу»).
- Прод-деплой мониторинга — по команде владельца через PIPELINE_PROD.

## Критерии приёмки

1. `pytest && ruff check . && ruff format --check . && mypy .` — зелёные
   (sites.yml проходит валидацию: https-only metrics_urls, kinds из whitelist).
2. После полной пересборки в `/metrics`:
   - `monitoring_uptime_status{site="zabor-i-naves.ru"}` = 1;
   - `monitoring_ssl_days_left{site="zabor-i-naves.ru"}` присутствует (~87);
   - `monitoring_site_metrics_up{site="zabor-i-naves.ru",kind="..."}` = 0
     (эндпоинты ещё не готовы — норма, ответ 404).
3. `GET /api/v1/sd/site-metrics/tracking` — relay-таргет `app:8088` с
   `__metrics_path__=/api/v1/relay/site-metrics/tracking/zabor-i-naves.ru`
   и лейблом `site="zabor-i-naves.ru"` (ADR-010 D3).
4. Дашборды «Обзор сайта», «Все сайты», «Бизнес сайта»: домен появляется
   в переменной `$site`.
5. Алерты: SiteDown НЕ firing (сайт жив); CollectorFailing firing по Метрике/
   Вебмастеру для zabor-i-naves.ru — ожидаемо до выдачи доступов.
6. Регрессия: da-dryclean.ru и эвакуация.online — метрики/коллекторы работают
   как раньше.
7. Секреты: `git grep` по новому ключу/токенам — пусто; ключ только в `.env` (chmod 600).
