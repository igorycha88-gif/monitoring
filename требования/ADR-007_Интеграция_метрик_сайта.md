# ADR-007: Интеграция с метриками сайтов da-dryclean (site-metrics)

> Статус: принято. Дата: 2026-08-18. Эпик: ЭПИК-9.

## Контекст

Сайт da-dryclean.ru (VPS 37.143.15.148, стек: nginx + Next.js frontend +
FastAPI services `tracking`/`content` + PostgreSQL 16, blue-green деплой)
экспортирует собственные бизнес-метрики (`tracking_events_total` и др.).
Требуется централизованный сбор в мониторинге: бизнес- + сервисные метрики
(сервер, БД), без открытия новых портов наружу.

Ограничения:
- Мониторинг работает и из локальной сборки, и с VPS 130.49.129.241 →
  доступ только через публичный HTTPS (443) сайта, любые внешние порты
  закрыты.
- Взаимодействие двух приложений должно аутентифицироваться общим ключом.

## Решение

### D1. Канал и защита (сторона сайта — по ЧТЗ сайта)

- Метрики сайта отдаются nginx'ом по путям:
  - `https://da-dryclean.ru/metrics/tracking` → 127.0.0.1:8020 (tracking)
  - `https://da-dryclean.ru/metrics/content`  → 127.0.0.1:$content_port (blue-green)
  - `https://da-dryclean.ru/metrics/node`     → 127.0.0.1:9100 (node_exporter)
  - `https://da-dryclean.ru/metrics/postgres` → 127.0.0.1:9187 (postgres_exporter)
- Аутентификация: заголовок `X-Monitoring-Key` (64 hex-символа, общий
  секрет). Неверный/отсутствующий ключ → 403. Только GET. Rate limit 10 r/s.
- Ключ хранится: на сайте — `/etc/nginx/conf.d/monitoring-key.conf`
  (chmod 600) + `/opt/app/.env`; в мониторинге — только `.env`
  (`SITE_METRICS_API_KEY`, chmod 600). Ключ никогда не попадает в код,
  коммиты и логи.

### D2. Модель конфигурации

`config/sites.yml` — новое поле `metrics_urls` у сайта:

```yaml
- domain: da-dryclean.ru
  metrics_urls:
    tracking: https://da-dryclean.ru/metrics/tracking
    content: https://da-dryclean.ru/metrics/content
    node: https://da-dryclean.ru/metrics/node
    postgres: https://da-dryclean.ru/metrics/postgres
```

Валидация (`app/sites.py`): ключи из whitelist
`{tracking, content, node, postgres}`; значения — строго `https://`
(секреты идут по публичному каналу), host обязателен, query/fragment
запрещены. Поле опционально: сайты без него не участвуют.

### D3. Скрейп Prometheus (расширение паттерна ADR-005/ЭПИК-6)

- Новый HTTP SD-эндпоинт: `GET /api/v1/sd/site-metrics/{kind}` — цели из
  `metrics_urls[kind]` всех сайтов; лейблы: `site`, `__scheme__=https`,
  `__metrics_path__` (path из URL), target `host:443`.
- 4 статических job'а в `prometheus.yml` (`site-tracking`, `site-content`,
  `site-node`, `site-postgres`), каждый — `http_sd_configs` на свой kind +
  `http_headers: X-Monitoring-Key` (Prometheus ≥ 2.90).
- Ключ в конфиге — плейсхолдер `__SITE_METRICS_API_KEY__`; подстановка при
  старте контейнера entrypoint-скриптом `prometheus-entrypoint.sh`
  (паттерн ADR-006 §3, как у alertmanager). Пустой env → заглушка
  `NOT_CONFIGURED`: контейнер стартует, скрейпы получают 403 → `up=0`.

### D4. Health-коллектор эндпоинтов (monitoring-app)

`SiteMetricsCollector` (`collectors/sitemetrics.py`, `source="site-metrics"`):

- Раз в 60 с (настройка `SITE_METRICS_INTERVAL_SECONDS`) проверяет каждый
  `metrics_urls[kind]` каждого сайта GET'ом с заголовком ключа.
- Метрики: `monitoring_site_metrics_up{site,kind}` (1 = HTTP 2xx),
  `monitoring_site_metrics_response_code{site,kind}` (0 — ответа нет),
  `monitoring_site_metrics_latency_seconds{site,kind}`.
- Философия ADR-002 (uptime): HTTP 403/5xx/сеть — это ДАННЫЕ (endpoint
  недоступен), а не ошибка коллектора: `collector_success=1`,
  `site_metrics_up=0`. Без ретраев — цикл 60 с сам является ретраем.
- `parallel = True`. Только для сайтов с заполненным `metrics_urls`.

### D5. Метрики сайта (спека — в ЧТЗ сайта, реализует команда сайта)

Бизнес-гейджи tracking (окна 24ч/1ч, пересчёт фоново раз в 60 с из БД;
counter'ы `tracking_events_total` остаются как есть):
`business_sessions_active`, `business_page_views_24h`, `_1h`,
`business_unique_visitors_24h`, `business_sessions_24h`,
`business_avg_session_duration_seconds_24h`, `business_bounce_rate_24h`,
`business_events_24h{event_type}`, `business_leads_24h`, `_1h`,
`business_conversion_rate_24h`, `business_referral_sources_24h{source}`,
`business_geo_visitors_24h{city}` (топ-10 + other),
`business_service_clicks_24h{service}` (топ-20).
Кардинальность лейблов ограничена (город ≤ 11 значений, услуга ≤ 21).

Сервисные: node_exporter (systemd, 127.0.0.1:9100), postgres_exporter
(docker, 127.0.0.1:9187, readonly-пользователь `pg_monitor`),
`content_http_requests_total{method,route,code}` +
`content_http_request_duration_seconds{method,route}` (route — шаблон
пути, не сырой path).

### D6. Алерты (расширение alerts.yml)

- `SiteMetricsEndpointDown`: `monitoring_site_metrics_up == 0` for 5m,
  warning — эндпоинт метрик недоступен (ключ/сеть/сервис).
- `SiteNoTraffic`: `business_page_views_24h == 0` for 3h, warning — сайт
  жив, но трекинг не фиксирует просмотры (сломан фронт-трекер или
  контент недоступен).

### D7. Дашборд

`grafana/dashboards/site-business.json` (uid `site-business`): 14 панелей —
просмотры/посетители/сессии/активные сессии/длительность/отказы/лиды/
конверсия/события по типам/источники (pie)/гео (таблица)/клики по услугам
(bar) + доступность и задержка эндпоинтов метрик. Переменная `site`,
datasource uid `prometheus`, без rate() на `monitoring_*`.

## Последствия

- Универсальный механизм: любой следующий сайт подключается одной записью
  `metrics_urls` в sites.yml (SD подхватывает за 60 с, без рестарта).
- Двойной канал (коллектор + Prometheus scrape) даёт независимые сигналы:
  бизнес-метрики живут в Prometheus (site-* jobs), доступность эндпоинтов —
  в monitoring-app.
- Риск: сайт ещё не доработан → до деплоя доработок `site_metrics_up=0`,
  алерт SiteMetricsEndpointDown в pending — ожидаемо, коммуникация
  пользователем.
