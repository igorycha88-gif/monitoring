# ЧТЗ: Алерты Prometheus + Alertmanager → Telegram (ЭПИК-7)

- Дата: 2026-08-18
- Маршрут: Аналитик → Архитектор ✅ → Аналитик → Разработчик → Тестировщик → DevOps
- Основание: BACKLOG.md ЭПИК-7 (TASK-070/071), ADR-006
- Решения пользователя: канал — Telegram; бот будет создан пользователем
  (инструкция — раздел 6); деплой — локальный, прод по отдельной команде.

## 1. Цель

Инциденты (сайт лежит, SSL истекает, трафик просел, коллектор не собирает,
сервер недоступен, приложение мониторинга умерло) автоматически превращаются
в алерты Prometheus и доставляются в Telegram-чат владельца.

## 2. Требования

### Функциональные

1. `prometheus/alerts.yml` — правила алертов из ADR-006 §1 (все 7, окна и
   severity строго по таблице ADR-006):
   - `SiteDown` — `monitoring_uptime_status == 0`, for 3m, critical
   - `SiteSslExpiringSoon` — `monitoring_ssl_days_left < 14`, for 1h, warning
   - `SiteSslExpiringCritical` — `monitoring_ssl_days_left < 3`, for 1h, critical
   - `SiteTrafficDrop` — `monitoring_site_visits_total{source="metrika"} <
     0.5 * (... offset 24h)` при вчерашних > 10, for 2h, warning
   - `CollectorFailing` — `monitoring_collector_success == 0`, for 15m, warning
   - `NodeExporterDown` — `up{job="node-exporter"} == 0`, for 5m, warning
   - `MonitoringAppDown` — `absent(monitoring_uptime_status)`, for 5m, critical
2. Аннотации на русском (`summary`, `description`) с `{{ $labels.site }}` /
   `{{ $labels.source }}` / `{{ $value }}`; у каждого алерта лейбл `severity`.
3. `prometheus/prometheus.yml`: `rule_files` → alerts.yml; `alerting` →
   `alertmanager:9093`.
4. Сервис `monitoring-alertmanager` (prom/alertmanager:v0.27.0, сеть
   `monitoring-net`, healthcheck `/-/healthy`, порт `127.0.0.1:9093`):
   - route: `group_by: [alertname, site]`, `group_wait: 30s`,
     `group_interval: 5m`, `repeat_interval: 12h`, receiver `telegram`;
   - `telegram_configs`: `send_resolved: true`, bot_token/chat_id из env;
   - inhibit: critical глушит warning по `site` (SSL-пара), SiteDown глушит
     SiteTrafficDrop/CollectorFailing того же сайта.
5. Секреты: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` — только `.env`;
   `.env.example` дополнен (с комментариями-инструкцией). Подстановка в
   конфиг — entrypoint-скриптом `alertmanager-entrypoint.sh` (ADR-006 §3);
   пустые значения → конфиг с заглушкой, контейнер стартует.
6. Плейсхолдеры `__TELEGRAM_BOT_TOKEN__` / `__TELEGRAM_CHAT_ID__` не
   встречаются в результирующем конфиге контейнера после подстановки.

### Технические

- Изменяемые файлы: `prometheus/alerts.yml`, `prometheus/alertmanager.yml`
  (шаблон), `prometheus/alertmanager-entrypoint.sh`, `prometheus/prometheus.yml`,
  `docker-compose.yml`, `.env.example`, `ARCHITECTURE.md` (порт/структура —
  уже обновлены Архитектором), `требования/BACKLOG.md` (статусы, DevOps).
- Нового Python-кода НЕТ (контур инфраструктурный); Python — только тесты
  конфигов: `tests/test_alerts.py`.
- Правило 8 (метрики/логи коллекторов) неприменимо к YAML-конфигам;
  проверка логов Alertmanager — этап DevOps.

## 4. Критерии приёмки

1. `pytest && ruff check . && ruff format --check . && mypy .` — зелёные.
2. Все 7 алертов из ADR-006 присутствуют с точными expr/for/severity
   (проверяется тестом по DoD TASK-070).
3. Тесты ловят: пропавший алерт, лишний rate(), незакреплённый rule_files,
   отсутствие env-передачи токена в compose, отсутствие healthcheck.
4. `promtool check rules` на alerts.yml и `amtool check-config` — без ошибок
   (шаг DevOps, внутри контейнеров образов prometheus/alertmanager).
5. Полная пересборка `docker compose -p monitoring` — все 4 сервиса healthy
   (app, prometheus, alertmanager, grafana).
6. `curl 127.0.0.1:9091/api/v1/rules` — правила загружены; фаза firing
   наблюдаема (при example.com/example.org SiteDown firing — ожидаемо,
   тестовые домены из sites.yml).
7. Токен/chat_id отсутствуют в файлах репозитория (кроме .env.example
   с пустыми значениями) и в логах.
8. Существующая функциональность не изменена (старые тесты зелёные).
9. После заполнения `.env` и пересоздания alertmanager тестовое
   уведомление доходит в Telegram (проверка пользователем по инструкции §6).

## 5. Ограничения и риски

- Порт 9093 — новый; проверка занятости (`ss -tlnp`) обязательна на каждом
  деплое (локально и на VPS, обновить PIPELINE_PROD pre-flight при проде).
- Без токена в `.env` Telegram-доставка не работает (алерты видны только в
  UI Prometheus) — осознанная деградация (ADR-006 §3).
- `example.com`/`example.org` в sites.yml — SiteDown будет постоянно firing
  до замены на реальные сайты; это тестовые данные, не блокер.
- Telegram Bot API доступен с VPS без прокси (риски блокировок IP-диапазонов
  хостеров не устраняем на уровне проекта).

## 6. Инструкция для пользователя (создание бота и chat_id)

1. В Telegram: @BotFather → `/newbot` → имя + username → получить token
   вида `1234567890:AA...`.
2. Написать своему боту любое сообщение (или `/start`).
3. Узнать chat_id: открыть
   `https://api.telegram.org/bot<TOKEN>/getUpdates` — в JSON поле
   `result[].message.chat.id` (для личного чата — положительное число).
4. Вписать в `.env` (chmod 600):
   ```
   TELEGRAM_BOT_TOKEN=1234567890:AA...
   TELEGRAM_CHAT_ID=123456789
   ```
5. Пересоздать alertmanager: `docker compose -p monitoring up -d --force-recreate alertmanager`
   (полная пересборка — при следующем полном деплое конвейера).
