# ЧТЗ: Хранение данных Вебмастера в БД с привязкой к сайту

- Дата: 2026-08-19
- Источник: запрос пользователя («данные должны храниться с привязкой к сайту»)
- Архитектура: `требования/ADR-009_Хранение_данных_Вебмастера_SQLite.md`
- Маршрут: Аналитик → Архитектор → Аналитик → **Разработчик → Тестировщик → DevOps**

## 1. Цель

Все данные, получаемые коллектором Вебмастера (недельный срез /popular и
дневная история per-query), сохраняются в SQLite с привязкой к сайту
(domain). История переживает пересборку/потерю Prometheus TSDB.

## 2. Что делаем

### TASK-BCK-1: Слой хранения `app/storage.py`

Класс `WebmasterStorage` (ADR-009 D2–D3):
- `__init__(path)`, `init()` — каталог, DDL двух таблиц, WAL, busy_timeout;
- `save_weekly(site, rows, fetched_at)` — INSERT OR REPLACE пачкой
  (одна транзакция на прогон сайта);
- `save_daily(site, rows)` — UPSERT по `(site, query_id, date)`;
- `close()`.
Типизация строгая; логирование (`storage_init`, `storage_weekly_written`,
`storage_daily_written`, ошибки).

### TASK-BCK-2: Интеграция в коллектор `collectors/webmaster.py`

- Параметр `storage: WebmasterStorage | None = None` (обратная совместимость).
- После `/popular`: `await asyncio.to_thread(storage.save_weekly, ...)`.
- В `_write_daily_row`/после разбора истории: `save_daily` c датой новейшей
  завершённой точки.
- Исключение записи: `logger.error("webmaster_db_write_failed", ...)` +
  инкремент `monitoring_storage_errors_total{source="webmaster"}` (новая
  метрика в `app/metrics.py`); сбор метрик продолжается (ADR-009 D4).

### TASK-BCK-3: Конфигурация и DI

- `app/config.py`: `webmaster_db_path: str = "data/webmaster.db"` (пустая
  строка = отключено).
- `app/main.py` lifespan: создание/init/close storage, передача в
  `WebmasterCollector`.
- `.env.example`: `WEBMASTER_DB_PATH` с комментарием.

### TASK-INF-1: Docker

- `docker-compose.yml`: volume `monitoring-db:/var/lib/monitoring`,
  env `WEBMASTER_DB_PATH=/var/lib/monitoring/webmaster.db` для app.
- `.dockerignore`: `data/`.

### TASK-TST-1: Автотесты (Правило 8)

- `tests/test_storage.py`: init создаёт таблицы; weekly сохраняет снапшоты
  (накопление по fetched_at); daily UPSERT идемпотентен и перезаписывает
  ретро-корректировки; привязка к сайту (данные двух сайтов не смешиваются);
  NULL-индикаторы; close().
- `tests/test_collector_webmaster.py` (существующий): подмена storage —
  проверка вызовов save_weekly/save_daily с нужными аргументами; ошибка
  storage не валит `collect_site` (метрики пишутся, errors_total растёт).
- Обновить тесты конфига/main при необходимости.

## 3. Ограничения

- API Яндекса, метрики Prometheus, дашборды — БЕЗ изменений.
- Чтение из БД (API/экспорт) — вне скоупа.
- Новых зависимостей нет (sqlite3 — stdlib).

## 4. Критерии приёмки

1. После прогона коллектора в БД есть строки обеих таблиц с корректным
   `site` (domain) из config/sites.yml.
2. Повторный прогон того же дня: daily-строки не дублируются (UPSERT),
   weekly-снапшоты накапливаются.
3. При ошибке записи в БД сбор метрик не падает; счётчик
   `monitoring_storage_errors_total` доступен на /metrics.
4. Файл БД persists в docker volume `monitoring-db` (переживает
   пересборку).
5. `pytest && ruff check . && mypy .` — зелёные; покрытие новых файлов ≥ 60%.
6. После деплоя: логи содержат `storage_*` события, ошибок нет.
