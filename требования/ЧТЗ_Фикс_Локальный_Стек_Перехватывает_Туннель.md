# ЧТЗ: Фикс «no data» в Grafana — локальный стек перехватывает порты SSH-туннеля до прода

> Маршрут 3 (инфраструктурная): Аналитик → DevOps. Упрощённая форма (малая задача).
> Дата: 2026-08-24. Постдеплойный рестарт №3.

## 1. Проблема

Пользователь открывает «User Analytics — zabor-i-naves.ru» и видит «no data»,
хотя прод-стек полностью здоров (данные подтверждены через Grafana API прода).

## 2. Диагностика

| Проверка | Результат |
|---|---|
| Прод: дашборд/данные | ✅ 9 панелей (новая версия), `sum(page_views_total)=1601`, семпл 16:51, таргеты site-content up, дубликатов дашборда нет |
| Локальная машина: `lsof -iTCP:3300` | ⚠️ занят `com.docker` — **локальный стек мониторинга запущен** (3300/8088/9091/9093) |
| Локальный Prometheus | 0 серий zabor; site-\* таргеты **down** (локальный app стартовал со старым ключом site-metrics — до фикса) |

**Корневая причина:** локальный dev-стек занимает `127.0.0.1:3300` →
`ssh -L 3300:...` не может забиндить порт → браузер по `localhost:3300`
открывает ЛОКАЛЬНУЮ Grafana без данных zabor, а не прод.

## 3. Изменения

1. Остановить локальный dev-стек: `docker compose -p monitoring down`
   (на локальной Mac; volumes сохраняются; прод не затрагивается — это
   разные машины).
2. Освободившиеся порты 3300/8088/9091/9093 → SSH-туннель до прода снова работает.

Код, конфиги, прод — БЕЗ изменений.

## 4. Критерии приёмки

- [ ] Локально `lsof -iTCP:3300` — пусто (порт свободен)
- [ ] Локальный `docker ps` — нет контейнеров monitoring-*
- [ ] Пользователь открывает туннель и видит прод-Grafana с данными
      (панели «всего» с ненулевыми значениями)

## 5. Риски

- Локальный стек остановлен как dev-окружение; при необходимости разработки
  поднимается `docker compose -p monitoring up -d` (но тогда туннель до прода
  нужно вести на других портах, например `-L 13300:127.0.0.1:3300`).
