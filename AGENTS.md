**Обязательные меры:**
- Файрвол: входящие — только SSH (22). Наши порты НЕ открывать наружу.
- Все сервисы мониторинга биндятся на `127.0.0.1`, НЕ на `0.0.0.0`.
- SSH: ключи, `PasswordAuthentication` не трогаем без отдельного решения, хост проверять по ключу `SHA256:g3xVlty76Op1vIbTuwy+8M+0ZUXx4XgtQX2+YrTtbLY`.

- Секреты (токены Яндекс.Метрики, ключи Вебмастера, пароль Grafana) — ТОЛЬКО в `.env` (chmod 600), НИКОГДА в коде/коммитах.
- Grafana: сменить admin-пароль при первом деплое, отключить anonymous-доступ.
- Пароли/токены из чата НЕ записывать в файлы репозитория и логи.

## 1. Конвейер работы (AI Team Pipeline) — АВТОМАТИЧЕСКИЙ

Формальная спецификация: `PIPELINE.js` (файл в корне проекта).

### Роли конвейера (5 ролей):

```
🏗️ АРХИТЕКТОР  — проектирует решения для сложных задач (условный этап)
📋 АНАЛИТИК    — анализирует задачу, создаёт ЧТЗ, маршрутизирует
💻 РАЗРАБОТЧИК — реализует код по ЧТЗ (Python/FastAPI коллекторы + Grafana)
🧪 ТЕСТИРОВЩИК — проверяет реализацию (код-ревью + автотесты + глубокая проверка)
🚀 DEVOPS      — собирает и деплоит (соблюдая изоляцию)
```

### Порядок этапов (зависит от маршрутизации):

**Маршрут 1: Стандартная задача (код/фича/баг-фикс):**
```
АНАЛИТИК → РАЗРАБОТЧИК → ТЕСТИРОВЩИК → DEVOPS
```

**Маршрут 2: Сложная задача (архитектурная):**
```
АНАЛИТИК → АРХИТЕКТОР → АНАЛИТИК → РАЗРАБОТЧИК → ТЕСТИРОВЩИК → DEVOPS
```

**Маршрут 3: Инфраструктурная задача (Docker, Prometheus, Grafana, firewall):**
```
АНАЛИТИК → DEVOPS (прямая задача)
```

**Маршрут 4: Постдеплойный рестарт (ошибка после деплоя):**
```
ПОЛЬЗОВАТЕЛЬ: «не работает» → АНАЛИТИК → РАЗРАБОТЧИК → ТЕСТИРОВЩИК → DEVOPS
```

### ⚡ ПРИНЦИП БЕСПЕРЕБОЙНОГО КОНВЕЙЕРА

**КРИТИЧЕСКИ ВАЖНО:** Переходы между ролями происходят **АВТОМАТИЧЕСКИ, БЕЗ ожидания подтверждения пользователя.**

Пользователь ставит задачу ОДИН раз — и конвейер идёт до конца:
```
Пользователь: «Задача»
  → Аналитик (анализ + маршрутизация)
  → [Архитектор (если сложная)] → Аналитик (ЧТЗ)
  → Разработчик (вопросы + код + тесты)
  → Тестировщик (проверка + глубокая проверка кода)
  → [если баги → Разработчик → Тестировщик, цикл]
  → DevOps (сборка + деплой)
  → ГОТОВО
  → [если пользователь нашёл ошибку → РЕСТАРТ с Аналитика]
```

**Правила переходов:**

| Переход | Условие | Действие |
|---------|---------|----------|
| Аналитик → Архитектор | Задача архитектурно сложная | Автоматически продолжить |
| Архитектор → Аналитик | ADR создан, решения спроектированы | Автоматически вернуться |
| Аналитик → Разработчик | ЧТЗ создано, исполнитель = Разработчик | Автоматически продолжить |
| Аналитик → DevOps | ЧТЗ создано, исполнитель = DevOps | Автоматически продолжить |
| Разработчик → Тестировщик | Код написан, `pytest && ruff && mypy` пройдены | Автоматически продолжить |
| Тестировщик → Разработчик (баг) | Найдены баги (NO-GO) | Автоматически передать баг-репорты |
| Разработчик → Тестировщик (рефикс) | Баг пофиксен, проверки пройдены | Автоматически вернуть на ретест |
| Тестировщик → DevOps | GO (все тесты пройдены, багов нет) | Автоматически продолжить деплой |
| DevOps → Завершение | Деплой успешен | Вывести итоговый отчёт |
| **Постдеплой: пользователь нашёл ошибку** | В ТОЙ ЖЕ сессии | **РЕСТАРТ с Аналитика** |

**Цикл баг-фикса работает автоматически:**
```
Тестировщик нашёл баги → 🔄 Разработчик фиксит → 🔄 Тестировщик проверяет → [повторять пока багов нет] → GO → DevOps
```

При каждом баг-фиксе Разработчик:
- Фиксит код
- Запускает `pytest && ruff check . && mypy .`
- АВТОМАТИЧЕСКИ возвращает Тестировщику

**Вопросы ролей — НЕ БЛОКИРУЮТ конвейер.** Каждая роль может задать вопросы через `question` tool, НО:
- Вопросы задаются **ТОЛЬКО когда по существу** — что-то неясно и есть несколько вариантов реализации
- Если всё понятно из контекста задачи — вопросы НЕ задаются, конвейер идёт дальше
- Если пользователь ответил — учесть ответы и продолжить
- Если пользователь не ответил в течение 2 минут — использовать рекомендуемый вариант (дефолт) и продолжить
- Никогда не останавливать конвейер в ожидании ответов

## 2. 8 железных правил (нарушение = остановка)

### ПРАВИЛО 1 — ВОПРОСЫ
Каждая роль может задать вопросы через `question` tool — но **ТОЛЬКО когда по существу**: что-то неясно и есть несколько вариантов.
Если всё понятно из контекста — вопросы не задаются, конвейер продолжает работу.
Если пользователь не ответил в течение 2 минут — использовать рекомендуемый вариант (дефолт) и продолжить.

### ПРАВИЛО 2 — ЧТЗ
Разработчик НЕ пишет код без утверждённого ЧТЗ.
Если задача поступила без ЧТЗ — сначала переключись в режим Аналитика, создай ЧТЗ.

### ПРАВИЛО 3 — ТЕСТЫ
Разработчик НЕ передаёт работу без прохождения:
```bash
pytest && ruff check . && mypy .
```

### ПРАВИЛО 4 — ПРИЁМКА
Тестировщик НЕ ставит GO без:
- Проверки ВСЕХ критериев из ЧТЗ
- **ГЛУБОКОЙ проверки кода** (чтение каждого изменённого файла, проверка логики)
- Проверки edge cases и error handling

### ПРАВИЛО 5 — РЕГРЕССИЯ
После фикса бага — проверяется окружающий функционал.

### ПРАВИЛО 6 — ПОЛНАЯ ПЕРЕСБОРКА (ТОЛЬКО НАШ СТЕК)
DevOps **ВСЕГДА** делает **ПОЛНУЮ пересборку ВСЕХ сервисов мониторинга** (monitoring-app, prometheus, grafana) после успешного тестирования.
**ЗАПРЕЩЕНА** частичная пересборка отдельных контейнеров.
**ЗАПРЕЩЕНО** пересобирать/трогать контейнеры СУЩЕСТВУЮЩЕГО приложения (см. 0.1).

### ПРАВИЛО 7 — ПОСТДЕПЛОЙНЫЙ РЕСТАРТ
Если после успешного деплоя пользователь сообщает об ошибке **В ТОЙ ЖЕ сессии**
(«не работает», «вижу ошибку», «баг», «сломалось» и т.д.) — конвейер **ПЕРЕЗАПУСКАЕТСЯ** с ЭТАПА 1 (Аналитик).
**ЗАПРЕЩЕНО** фиксить «на месте» без прохождения полного конвейера.
См. `PIPELINE.js → POSTDEPLOY_RESTART`.

### ПРАВИЛО 8 — АВТОТЕСТЫ, ЛОГИРОВАНИЕ, МЕТРИКИ (ОБЯЗАТЕЛЬНО)

**Разработчик НЕ передаёт работу без:**

1. **Автотестов** на КАЖДЫЙ реализованный функционал:
   - Unit-тесты для коллекторов: happy path + error cases + edge cases
   - Unit-тесты для API routes: валидация, статусы ответов
   - Тесты на ретраи/лимиты внешних API (Метрика 429, Вебмастер ошибки)
   - Тесты на логирование (проверить что logger вызывается)
   - Покрытие ≥ 60% для новых файлов
   - Если автотестов нет → работа НЕ принимается

2. **Логирования** во ВСЕ реализованные файлы:
   - API routes: логировать request (method, path) и response (status, duration)
   - Коллекторы: логировать начало/конец цикла сбора, количество собранных точек, ошибки
   - Каждый catch-блок: `logger.error({error, context, operation})` через `structlog`/стандартный logger
   - Если логирования нет → работа НЕ принимается

3. **Метрик** для каждого коллектора:
   - `monitoring_collector_success{source, site}` / `monitoring_collector_errors_total{source, site}`
   - `monitoring_collector_duration_seconds{source, site}`
   - Если метрик нет → работа НЕ принимается

**Тестировщик:**
4. Запускает автотесты и проверяет достаточность покрытия
5. При наличии багов → АВТОМАТИЧЕСКИ переводит на Разработчика
6. Разработчик фиксит → АВТОМАТИЧЕСКИ возвращает на ретест
7. Цикл повторяется пока ВСЕ автотесты не пройдут и багов не будет

## 5. Формат каждого этапа

### Этап 0 — Архитектор (условный, только для сложных задач):

1. Выведи: `🏗️ АРХИТЕКТОР: Начинаю архитектурный анализ задачи`
2. Изучи текущую архитектуру (ARCHITECTURE.md, config/sites.yml, collectors/, grafana/dashboards/)
3. Спроектируй решение: модель данных Prometheus, коллекторы, API, дашборды, файловая структура
4. Создай Architecture Decision Record (ADR)
5. Обнови ARCHITECTURE.md если нужно
6. **АВТОМАТИЧЕСКИ вернись к Аналитику** с результатами

**Скилл:** `SKILL_ARCHITECT.md`

**Когда привлекается (решение Аналитика):**
- Новый источник данных (новый коллектор: Метрика/Вебмастер/uptime/серверные)
- Новый API-контекст (>3 endpoints)
- Изменение архитектуры проекта
- Интеграция с новым внешним API
- Затрагивает >5 файлов
- Влияет на нагрузку на внешние API (лимиты)

### Этап 1 — Аналитик:

1. Выведи: `📋 АНАЛИТИК: Начинаю работу над бизнес-задачей`
2. Прочитай существующую архитектуру и код проекта
3. **ОПРЕДЕЛИ МАРШРУТ:**
   - Нужен Архитектор? Если да → Этап 0 → затем вернуться сюда
   - Исполнитель после ЧТЗ: Разработчик или DevOps?
4. Задай вопросы пользователю (через `question` tool) — **только если что-то неясно**. Если всё понятно — пропусти
5. Дождись ответов (или используй дефолтные значения)
6. Создай ЧТЗ по шаблону из `SKILL_ANALYST.md` → сохрани в `требования/ЧТЗ_[Название].md`
   - **Включи блок маршрутизации** в ЧТЗ
7. Создай декомпозицию задач (TASK-XXX-YYY)
8. Выведи краткий макет/описание ЧТЗ пользователю
9. **МАРШРУТИЗАЦИЯ:**
   - Разработчик → АВТОМАТИЧЕСКИ переходи к Этапу 2
   - DevOps → АВТОМАТИЧЕСКИ переходи к Этапу 4 (прямая задача)

**Скилл:** `SKILL_ANALYST.md`

### Этап 2 — Разработчик (Python/FastAPI):

1. Выведи: `💻 РАЗРАБОТЧИК: Начинаю реализацию по ЧТЗ`
2. Задай вопросы по ЧТЗ (через `question` tool) — **только если что-то неясно**. Если всё понятно — пропусти
3. Дождись ответов (или используй дефолтные значения)
4. Реализуй задачи в порядке: TASK-BCK → TASK-FRT → TASK-INF
5. **ОБЯЗАТЕЛЬНО добавь логирование** во все реализованные файлы (структурированный logger). См. `SKILL_DEVELOPER.md → Логирование`
6. **ОБЯЗАТЕЛЬНО напиши автотесты** на КАЖДЫЙ реализованный функционал (happy path + error cases + edge cases + тесты на логирование + тесты на моки внешних API). Покрытие ≥ 60%
7. Запусти: `pytest && ruff check . && mypy .`
8. Если проверки упали — исправь и перезапусти
9. **АВТОМАТИЧЕСКИ переходи к Этапу 3 (Тестировщик)**

**Скилл:** `SKILL_DEVELOPER.md`

### Этап 3 — Тестировщик:

1. Выведи: `🧪 ТЕСТИРОВЩИК: Начинаю проверку`
2. Задай вопросы по плану тестирования (через `question` tool) — **только если что-то неясно**. Если всё понятно — пропусти
3. Создай тест-кейсы по критериям приёмки из ЧТЗ
4. **Запусти автотесты: `pytest && ruff check . && mypy .`**
5. **ПРОВЕРЬ АВТОТЕСТЫ:**
   - Покрывают ли ВСЕ реализованные функции из ЧТЗ?
   - Есть ли тесты на happy path, error cases, edge cases?
   - Есть ли тесты на логирование и моки внешних API?
   - Если покрытие недостаточное → NO-GO (баг: «Недостаточное покрытие тестами»)
6. **ГЛУБОКАЯ ПРОВЕРКА КОДА (обязательно):**
   - Прочитай КАЖДЫЙ изменённый файл
   - Сверь реализацию с требованиями ЧТЗ построчно
   - Проверь edge cases, error handling, безопасность (секреты не в коде!)
   - Проверь коллекторы, API routes, конфиги Prometheus/Grafana
   - **ПРОВЕРЬ ЛОГИРОВАНИЕ И МЕТРИКИ** (см. Правило 8)
   - (подробно см. `SKILL_TESTER.md` → Шаг 3.5)
7. Зарегистрируй баги (если есть)
8. Составь Test Summary Report
9. Выдай рекомендацию: GO / NO-GO / CONDITIONAL GO
10. **Если NO-GO / CONDITIONAL GO с багами → АВТОМАТИЧЕСКИ переходи к Разработчику с баг-репортами, цикл повторяется**
11. **Если GO → АВТОМАТИЧЕСКИ переходи к Этапу 4 (DevOps)**

### Этап 4 — DevOps (АВТОМАТИЧЕСКИЙ, ПОЛНАЯ ПЕРЕСБОРКА НАШЕГО СТЕКА):

1. Выведи: `🚀 DEVOPS: Начинаю полную пересборку и деплой стека мониторинга`
2. **НЕ задавать вопросов пользователю.** Все параметры определяются автоматически:
   - Compose-файл: `docker-compose.yml` в корне проекта (project name = `monitoring`)
   - Перед стартом: проверить что порты 8088/9091/3300 свободны (`ss -tlnp`)
3. **ПОЛНАЯ ПЕРЕСБОРКА ВСЕХ СЕРВИСОВ МОНИТОРИНГА:**
   ```bash
   docker compose -p monitoring build --no-cache
   docker compose -p monitoring up -d --force-recreate
   ```
   **ЗАПРЕЩЕНО:** пересобирать только один сервис; трогать чужие контейнеры.
4. Дождись healthcheck ВСЕХ сервисов:
   ```bash
   docker compose -p monitoring ps
   ```
   Все сервисы должны быть `healthy`. Таймаут 60 сек.
5. Проверь логи на отсутствие ошибок:
   ```bash
   docker compose -p monitoring logs --tail=50
   ```
   Искать: `error`, `fatal`, `ECONNREFUSED`, `Traceback`, `OOM`
6. **ПОЛНАЯ ПРОВЕРКА ДОСТУПНОСТИ:**
   ```bash
   curl -f http://127.0.0.1:8088/health
   curl -f http://127.0.0.1:8088/metrics | head -20
   curl -s http://127.0.0.1:9091/-/healthy
   curl -s http://127.0.0.1:3300/api/health
   ```
7. Если всё прошло → выведи итог:
   ```
   ✅ Образы собраны (monitoring-app)
   ✅ Контейнеры запущены и healthy
   ✅ App /health OK (127.0.0.1:8088)
   ✅ /metrics отдаёт метрики
   ✅ Prometheus healthy (127.0.0.1:9091)
   ✅ Grafana healthy (127.0.0.1:3300)
   ✅ Существующее приложение НЕ затронуто
   🎉 Деплой завершён успешно
   ```
8. Если ошибка → ОТКАТ: не перезапускать автоматически, вывести детальный лог ошибки, предложить диагностику

**Скилл:** `SKILL_DEVOPS.md`
